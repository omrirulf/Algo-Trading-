---
title: "The Horse Race"
description: "The model, a coded rule and a coin flip, on the same lines against the same realised returns"
---

Every signal this system has ever traded on came from a model. The question
underneath the whole cost conversation — and underneath whether to keep a
model in the daily loop at all — is whether the model's judgement beats a
fixed rule reading only the price. `analysis/horse_race.py` is the thing that
asks it, and `rules/` is the rule.

```bash
python analysis/horse_race.py
python analysis/horse_race.py --horizon 5 --floor 0.5
```

It runs on its own, credential-free, every trading night after the close
(**Actions → horse race**), and on any pull request that touches an arm. It
reads the journal, fetches prices, and prints. It cannot trade and it cannot
move a parameter.

## The three arms

| Arm | What it is | Where it comes from |
| --- | --- | --- |
| **model** | The full model's answer, exactly as journalled | `logs/signal_journal.log` |
| **momentum** | Time-series momentum with the textbook parameters | `rules/momentum.py`, recomputed from the line's own technicals |
| **random** | A coin flip, seeded from the ticker and the day | `rules/control.py`, recomputed the same way |

Each arm is put through the identical conviction floor, the identical stop and
sizing arithmetic (`backtest.simulate.simulate_trade`, the code that actually
trades), and scored against the identical price history. The only thing that
differs between the rows is the judgement.

**The random row is the number the other two are really measured against.**
It is what taking a side with no information scores on these names over these
windows. In a week the index rose 2%, "always long" hit 78% of the time
without knowing anything about anything — so an arm that cannot beat the coin
flip is not reading the market, it is being carried by it. The buy-and-hold
rows say what the direction of the market alone was worth.

## What the rule reads, and why that is the point

The momentum arm reads one thing: the `TechnicalSnapshot` the cycle already
computed from price history and already showed the model in its prompt. No
news, no fundamentals, no analysts, no insiders. That is not a limitation of
the rule; it is the experiment. The model sees all of those too. If the model
does not beat a rule that sees strictly less, then reading the rest bought
nothing.

Because both arms read the same snapshot at the same instant, there is no
look-ahead to worry about: the rule cannot know anything the model did not
also know at that moment, by construction.

The rule itself, from Moskowitz, Ooi and Pedersen (*Journal of Financial
Economics*, 2012) and its short-horizon form in Medhat and Schmeling (*Review
of Financial Studies*, 2022):

- **BULLISH** when the 63-bar return is positive *and* price is above its
  50-day average; **BEARISH** when both are negative; **NEUTRAL** when they
  disagree. Requiring both is the standard trend-confirmation filter.
- **Conviction** is the quarter's return in units of volatility, so a 10%
  move in a 15%-vol fund counts for more than the same move in a 60%-vol
  single name. Full conviction is a two-quarterly-sigma move — and since
  2·√(63/252) = 1, that is simply `|return_63d| / annualised_volatility`,
  clamped to [0, 1].

<Warning>
  **Nothing in the rule is fitted to this journal, and nothing will be.** 63
  bars is a quarter. 50 is the confirmation average the literature uses. Two
  sigmas is the choice that leaves no leftover constant. None of them was
  picked by looking at what this journal would then say, and the race judges
  the rule rather than tuning it. A rule re-fitted on the returns it is then
  scored against is the overfitting machine the second opinion warned about,
  and this is the one place in the project where *leave it alone* is the
  whole method. A good number in the race is not a reason to start.
</Warning>

## Who gets asked

Every arm is offered every line, except the lines no arm was offered: a
ticker already in the book, where the model was never asked and a rule
holding the same book would not have been either. Those are excluded from
every arm alike.

The model then answers on **fewer** lines than the rules, and the coverage
table says so:

```
arm         offered  took a side  acted on  simulated  dropped
model           413           52        48         46        2
momentum        413          171        97         95        2
random          413          413       413        409        4
```

That asymmetry is by design, not an unfairness to correct. The screen drops
lines before the model sees them, and the model fails on some it does see;
both are the model's to own, because the funnel is part of the design being
raced. A race that only ran on the lines the model chose to answer would be
handing the model the choice of battlefield.

## The arms are on every journal line

Since this page's PR merged, every line the heartbeat writes carries an
`arms` field beside the model's signal — on screened lines, held lines and
failed lines too, computed inside `journal.record` itself so no call site can
leave it off:

```json
"arms": {
  "momentum": {"bias": "BULLISH", "conviction": 0.41, "rationale": "63d return +8.2% is 0.41x annual vol 20.1%; price +3.1% vs 50d SMA"},
  "random":   {"bias": "BEARISH", "conviction": 0.5,  "rationale": "random: coin flip seeded from ticker and day"}
}
```

Nothing in the cycle reads it back. The signal handed to the engine is the
model's, untouched, and CI pins that the same way it pins the learned blend:
`rules/` cannot reach an order path, write a file or read a credential, and
the arms' output may be read only by the module that computes it and the
journal that writes it down.

The harness does not trust that field, though. It recomputes both rule arms
from the `technicals` on each line, which is what lets it race the model over
every line ever journalled — including everything written before the arms
existed — and is why the coin flip is seeded from the day rather than a
clock: two runs of the race disagree only when the journal or the prices did.

## Reading the table

```
arm             n   hit rate    median      mean  stopped out
model          46     +37.0%     -0.1%     -0.1%        +2.2%
momentum       95     +54.7%     +0.4%     +0.5%        +3.2%
random        409     +51.1%     +0.2%     +0.2%        +2.9%  

Direction agreement, model vs momentum, where both took a side: +48.0% (n=25)
```

Read it in this order:

1. **Does anything beat `random`?** If not, nothing is reading the market.
2. **Does `model` beat `momentum`?** If not, the daily model call is buying
   nothing a fixed rule does not already give — which is the whole question.
3. **Direction agreement** says whether the two are even making different
   calls. High agreement with a worse result means the model is momentum
   plus noise; low agreement means it is genuinely doing something else, for
   better or worse.

The numbers above are illustrative. The real ones are in the latest run's
summary, and they change nightly as outcomes resolve.

## Limits

This is per-trade, not a portfolio, for the same reason
[baseline_compare](/scoring) is: no overlapping positions, no cash
constraints, no compounding. It cannot say what an account following each arm
would be worth today; building that means choosing a position-sizing and
overlap policy that would shape the answer as much as measure it.

Anything marked *too few* is arithmetic, not evidence. And a week's worth of
trades all inside one market regime is far fewer independent observations
than the `n` column suggests — the second opinion's arithmetic on this was
that separating a real 55% from a coin flip takes on the order of 800
independent trades, and this system takes a few dozen a week. The race is
built to run nightly for as long as that takes, which is the point of
running it on a schedule rather than when someone remembers to ask.
