`config/settings.py` is the single source of truth for the whole system,
and it draws a hard line between two kinds of values.

<Warning>
  **Guardrails are not configuration.** `MAX_POSITION_PCT`, `MIN_CONVICTION`,
  and friends are Python `Final` constants in `config/settings.py`, not
  environment variables. A misconfigured or compromised `.env` file cannot
  loosen them — see [Guardrails](/guardrails). Changing a guardrail requires
  a code change that shows up in a diff and in review.
</Warning>

## Environment variables (`.env`)

These are secrets and per-deployment wiring — the things that legitimately
differ between your machine and someone else's, and that have no business
being hard-coded.

| Variable | Used by | Description |
|---|---|---|
| `ALPACA_API_KEY` | `app/broker_client.py` only | Alpaca **paper** API key. Optional if you use `alpaca profile login` instead — see below. |
| `ALPACA_SECRET_KEY` | `app/broker_client.py` only | Alpaca **paper** API secret. Optional if you use `alpaca profile login` instead — see below. |
| `ALPACA_PROFILE` | `app/broker_client.py` only | Which Alpaca CLI profile to read. Default: the CLI's own default, else `paper`. |
| `ALPACA_CONFIG_DIR` | `app/broker_client.py` only | Where the Alpaca CLI keeps its state. Default: `~/.config/alpaca`. |
| `WEBHOOK_SHARED_SECRET` | `app/main.py`, `orchestrator/heartbeat.py` | Shared secret required in the `x-webhook-secret` header. Generate with `python -c "import secrets; print(secrets.token_hex(32))"`. |
| `WEBHOOK_URL` | `orchestrator/heartbeat.py` | Where the orchestrator POSTs signals. Default: `http://localhost:8000/webhook/signal`. |
| `WATCHLIST` | `orchestrator/heartbeat.py` | Comma-separated tickers evaluated every cycle. Defaults to the curated list in `config/watchlist.py` — see [Watchlist](/watchlist). |
| `BRIGHTDATA_API_TOKEN` | `orchestrator/news.py` only | Bright Data API token, from *Account settings → API tokens*. Optional if you use `brightdata login` instead — see below. |
| `BRIGHTDATA_SERP_ZONE` | `orchestrator/news.py` only | Name of your Bright Data **SERP API** zone. Empty by default, so the unlocker fallback below can fire. |
| `BRIGHTDATA_UNLOCKER_ZONE` | `orchestrator/news.py` only | Web Unlocker zone to use when no SERP zone is set — e.g. `cli_unlocker`, which `brightdata login` creates. |
| `ANTHROPIC_API_KEY` | `orchestrator/llm.py` only | Claude API key, from the [Anthropic Console](https://console.anthropic.com). Optional if you use `ant auth login` instead — see below. |
| `SCREENING_BASE_URL` | `orchestrator/heartbeat.py` | OpenAI-compatible endpoint to run the *screening* stage against, e.g. `http://10.0.0.5:11434/v1`. Blank screens with Claude Haiku as before. Cannot be a model on the hosted runner — see [cost](/cost#a-stage-that-is-not-billed-at-all), and [concrete Gemini/Groq values](/cost#very-cheap-often-beats-free-for-this-workload) if you'd rather not self-host. |
| `SCREENING_MODEL` | `orchestrator/heartbeat.py` | Model name to ask that endpoint for, e.g. `qwen2.5:14b`. Required alongside `SCREENING_BASE_URL`, ignored without it — on its own it would let an env var silently change which Claude model screens the watchlist. |
| `SCREENING_EFFORT` | `orchestrator/heartbeat.py` | Ask the screening endpoint *with* reasoning on, at `low`, `medium` or `high`. Blank — the default — asks with reasoning off, which is what makes the stage cheap. Ignored without `SCREENING_BASE_URL`, because Claude Haiku takes neither adaptive thinking nor an effort. Only for endpoints that reason by default and have no true off switch; see [cost](/cost#very-cheap-often-beats-free-for-this-workload). **Never set it without a `compare_screening.py --effort` run at the same value** — a screen that wrongly answers NEUTRAL ends the ticker with no error anywhere. |
| `SCREENING_API_KEY` | `orchestrator/heartbeat.py` | Bearer token for that endpoint, if it wants one. Blank sends no header at all. |

<Note>
  Each credential is readable by exactly one module. `app/broker_client.py`
  is the only place `ALPACA_API_KEY` is read; `orchestrator/news.py` is the
  only place `BRIGHTDATA_API_TOKEN` is read, and `broker_client.py` is
  likewise the only reader of the Alpaca CLI profile. This isolation is
  checked by CI, not just by convention — see [Guardrails](/guardrails).
</Note>

## All three credentials have a CLI alternative

None of them has to be copied out of a web dashboard. Each can be obtained by
logging in on the command line instead:

| Credential | CLI | What it does |
|---|---|---|
| `ANTHROPIC_API_KEY` | `ant auth login` | SDK resolves the stored profile itself. |
| `BRIGHTDATA_API_TOKEN` | `brightdata login` | OAuth in the browser (`--device` when headless), key stored locally. |
| `ALPACA_API_KEY` / `ALPACA_SECRET_KEY` | `alpaca profile login` | OAuth in the browser, profile stored in `~/.config/alpaca/profiles/` at `0600`. |

```bash
ant auth login          # once, on the machine that runs the heartbeat
brightdata login        # likewise; --device for a machine with no browser
alpaca profile login    # paper by default; see the warning below
# leave all three keys blank in .env
```

### Claude

`orchestrator/llm.py` passes `api_key or None` to the SDK, so a blank
`ANTHROPIC_API_KEY` doesn't fail — it defers to whatever the SDK can resolve
on its own: `ANTHROPIC_AUTH_TOKEN`, an `ant auth login` profile, or Workload
Identity Federation, in that order.

### Bright Data

`orchestrator/news.py` resolves its token in order: `BRIGHTDATA_API_TOKEN`,
then `BRIGHTDATA_API_KEY` (the variable the CLI itself reads, so a shell
already set up for the CLI needs no second variable for the same secret),
then the key `brightdata login` left in `~/.config/brightdata-cli/credentials.json`
(with the platform-appropriate path on macOS and Windows).

The zone resolves the same way: `BRIGHTDATA_SERP_ZONE`, then
`BRIGHTDATA_UNLOCKER_ZONE`.

<Note>
  **A Web Unlocker zone is enough — no dashboard visit required.**
  `brightdata login` provisions `cli_unlocker`, not a SERP API zone, but
  Bright Data's own CLI sends search queries through an unlocker zone by
  preference: its `search` command resolves `BRIGHTDATA_SERP_ZONE` and then
  falls back to `BRIGHTDATA_UNLOCKER_ZONE`, and its `init` offers the unlocker
  zone as the SERP default with *yes* preselected. Setting
  `BRIGHTDATA_UNLOCKER_ZONE=cli_unlocker` after the login is a complete setup.
  See [News](/orchestrator/news).
</Note>

<Warning>
  That was read from the CLI's source, not confirmed against a live call.
  If an unlocker zone is refused for search on your account, the symptom is a
  `NewsFetchError` about HTML instead of JSON, and the fix is a SERP API zone
  in the dashboard with `BRIGHTDATA_SERP_ZONE` set.
</Warning>

<Note>
  Reading the CLI's credential file is **best-effort**. Bright Data doesn't
  document its format, so the lookup tries several plausible field names
  (`api_key`, `apiKey`, `token`, …), searches a few levels deep in case the
  file nests them, and treats a missing file, bad JSON, an unrecognised shape
  or a permissions error as "not configured this way" rather than an error.
  If it guesses wrong on your machine, set `BRIGHTDATA_API_TOKEN` explicitly
  and nothing else changes.
</Note>

### Alpaca

`app/broker_client.py` resolves credentials as an **atomic bundle** — a key
from one source is never paired with a secret from another, because the
winning source decides which auth headers get sent. The order is:

1. `ALPACA_API_KEY` + `ALPACA_SECRET_KEY` (both required; setting only one is
   an error, not a silent fallthrough)
2. The profile's OAuth `access_token`, sent as `Authorization: Bearer …`
3. The profile's stored `api_key` + `secret_key`, sent as `APCA-API-KEY-ID` /
   `APCA-API-SECRET-KEY`

This mirrors the CLI's own resolution order, and both header schemes are
exactly the ones the CLI sends, so either kind of stored login works with the
`alpaca-py` SDK this project uses.

<Warning>
  **A profile that targets live trading is refused, not used.** If the profile
  carries `live_trade: true`, `resolve_credentials()` raises `BrokerError`
  naming the profile and the ways out. This system is paper-only; borrowing a
  live bundle would point real money at a strategy whose entire safety
  argument is that it cannot reach a live endpoint.

  The refusal is loud rather than silent on purpose. Reporting "no credentials
  found" on a machine that plainly has some would send you looking for ways to
  make the profile *more* reachable — the exact opposite of what you want.
</Warning>

<Note>
  This is belt-and-braces. `TradingClient(paper=True)` is hard-coded, and the
  SDK pins its base URL to the paper endpoint from that flag alone — so even a
  live key that somehow reached the constructor could not trade a funded
  account. CI checks both the hard-coded `paper=True` and the presence of the
  `live_trade` refusal.
</Note>

<Note>
  Unlike the Bright Data lookup, this one is **verified against the CLI's
  source** (`alpacahq/cli`, `internal/config/config.go`) rather than guessed:
  the file is YAML at `<config dir>/profiles/<name>.yaml`, the fields are
  `api_key`, `secret_key`, `access_token`, `scopes` and `live_trade`, and the
  config directory is `$ALPACA_CONFIG_DIR` or `~/.config/alpaca` on every
  platform — the CLI builds that path unconditionally, so there is no
  macOS/Windows special case. A missing file, bad YAML, an unrecognised shape
  or a permissions error is treated as "not configured this way".
</Note>

<Warning>
  This is a good fit for **running the heartbeat yourself, locally** — the
  profile is tied to your own login. An unattended deployment (a server, a
  container, a scheduled job nobody is watching) should still set an
  explicit `ANTHROPIC_API_KEY`, since there's no session for it to inherit.
</Warning>

Nothing fails silently either way: `AnthropicSignalProvider.__init__` never
raises, because the SDK doesn't validate credentials until the first request
is built. That check is a synchronous, no-network `TypeError` inside the SDK
itself — `orchestrator/llm.py` catches it and re-raises as `LLMError` with a
message naming both `ANTHROPIC_API_KEY` and `ant auth login`, so a ticker
with nothing resolvable logs a clear reason and is skipped, the same as any
other `LLMError`. `tests/test_llm.py` proves this happens without opening a
connection.

<Warning>
  **The market context adds nothing to this table.** Technicals, fundamentals
  and the analyst view all come from yfinance, which is unauthenticated, so
  `orchestrator/context.py` and its parsers read no setting, key or
  token at all — and CI greps them to keep it that way. If a future data
  source needs a credential, it needs a new module, not a new import in
  those four. See [Market Context](/orchestrator/market-context).
</Warning>

`Settings` is a `pydantic-settings` `BaseSettings` subclass that reads
`.env` then the process environment, and is constructed lazily via
`get_settings()` — importing `config.settings` never touches disk or the
network by itself.

## Guardrail constants (code, not `.env`)

These live in the same file but are never read from the environment. Full
detail on what each one prevents is in [Guardrails](/guardrails).

| Constant | Value | Meaning |
|---|---|---|
| `MAX_POSITION_PCT` | `0.05` | Max fraction of equity in one **single name**, including existing exposure. |
| `MAX_BROAD_FUND_PCT` | `0.12` | Cap for a diversified **broad fund**. |
| `MAX_FOCUSED_FUND_PCT` | `0.07` | Cap for a **focused fund** — one sector or one country. Measured 2026-09-15. |
| `MAX_COMMODITY_FUND_PCT` | `0.04` | Cap for a **single-commodity** fund — tighter than a single stock. |
| `MAX_EXPOSURE_GROUP_PCT` | `0.25` | Cap on any one exposure group, spanning every sleeve. |
| `EXPOSURE_GROUP_CAP_OVERRIDES` | `{"Duration": 0.30}` | Per-group exceptions to `MAX_EXPOSURE_GROUP_PCT`. Duration holds the four Treasury maturities plus `LQD`, and its number is set by what the bucket can lose: worst fall 18.9% (2022), so 30% risks about 5.7% of the account — less than an equity group at 25% risked in 2008. |
| `MAX_EQUITY_RISK_PCT` | `0.60` | Ceiling on **net** stock-market risk across every equity group at once, counted in beta-weighted dollars. Longs add and shorts subtract inside the stock bucket only; bonds and commodities never offset stocks. |
| `MAX_SINGLE_NAME_SLEEVE_PCT` | `0.25` | Budget for the whole single-name sleeve. |
| `MAX_FUND_SLEEVE_PCT` | `0.7` | Budget for the whole fund sleeve — the core allocation. |
| `MAX_GROSS_EXPOSURE_PCT` | `0.95` | Ceiling on total deployed capital across every position. Leaves a 5% operational buffer. |
| `MIN_CONVICTION` | `0.30` | Signals below this are rejected before any market data is fetched. Was 0.60; lowered to where the model actually starts taking a side. |
| `PROFIT_LADDER` | `+1R: sell ⅓, stop→entry · +3R: sell ⅓, stop→+1R` | How a winning position is unwound. R is entry-to-stop distance. See [Position management](/position-management). |
| `MAX_OPEN_POSITIONS` | `40` | Max distinct tickers held at once. Raised from 20 with the profit ladder: a trimmed runner keeps its slot, and the count must not block the cash the ladder frees. |
| `SKIP_HELD_TICKERS` | `True` | A ticker already in the book is asked nothing, by either model — the ladder and its stop manage it instead. Falls back to reviewing everything if the book cannot be read. See [cost](/cost#stage-zero-what-the-book-already-holds). |
| `USE_BATCH_API` | `True` | Ask both model stages through the Message Batches API at half price. The cycle starts pre-market so the waiting happens outside the session. See [cost](/cost#half-price-for-waiting). |
| `BATCH_DEADLINE_SECONDS` | `2100` | How long to wait on **one** batch before paying full price for whatever it has not answered — applied once for the screen and once for whatever it escalates, so the job's timeout has to cover it twice. |
| `ATR_PERIOD` | `14` | Wilder ATR lookback, in trading days. |
| `ATR_STOP_MULTIPLIER` | `2.0` | Stop-loss distance from entry, in multiples of ATR. |
| `MIN_ATR_PCT_OF_PRICE` | `0.002` | Below this, ATR is treated as degenerate data and the signal is rejected. |
| `OHLC_LOOKBACK_DAYS` | `90` | Daily history pulled for the ATR calculation. |
| `MIN_ORDER_QTY` | `1` | Fractional shares are never used. |
| `HEARTBEAT_INTERVAL_MINUTES` | `60` | Orchestrator cadence. |

## Log paths (code, not `.env`)

Also `Final` constants in `config/settings.py`, both under `LOG_DIR`
(`<project root>/logs`). They are separate files because they answer separate
questions:

| Constant | Path | Written by |
|---|---|---|
| `AUDIT_LOG_PATH` | `logs/execution_audit.log` | `app/logger.py` — what the *engine* did with each signal. |
| `SIGNAL_JOURNAL_PATH` | `logs/signal_journal.log` | `orchestrator/journal.py` — what the *model* saw before it produced one. |

See [Signal Journal](/orchestrator/journal) for why the second one exists and
what it makes answerable.

## Market-context constants (code, not `.env`)

`orchestrator/context.py` pins its fetch behaviour as module constants:

| Constant | Value | Meaning |
|---|---|---|
| `HISTORY_PERIOD` | `"2y"` | Daily history per ticker — enough to warm up a 200-day average and cover a 52-week range. |
| `SLOW_DATA_TTL_SECONDS` | `6 * 60 * 60` | How long fundamentals, ratings and ownership are cached per ticker. Price history is refetched every cycle. |
| `MAX_GAP_DETAIL` | `120` | Characters of failure text carried into the prompt's `DATA GAPS` section; the full text still reaches the log. |
