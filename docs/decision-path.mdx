title: "Decision Path"
description: "The nine checks a signal passes through in ExecutionEngine.execute()"
---

Every signal that reaches `app/main.py` runs through `ExecutionEngine._execute()`
in this exact order. Any gate can end the request with a `REJECTED` result;
any broker, market-data, or risk-math exception becomes an `ERROR` result.
Neither path ever raises out of `execute()` — see
[the safety net](#nothing-ever-raises) at the bottom of this page.

<Note>
  **Two fields decide everything: `bias` and `conviction`.** A signal now also
  carries `news_score`, `technical_score`, `fundamental_score`,
  `analyst_score` and `key_factors`, but not one of them appears anywhere
  below — they are recorded for later evaluation and read by nothing in
  `execution_engine.py` or `risk_engine.py`. A CI grep over those modules
  fails the build if that stops being true, so the decision path is exactly
  as wide as it was before the model started explaining itself.
</Note>

<Steps>
  <Step title="NEUTRAL means do nothing">
    `NEUTRAL` is a valid, honest thing for the LLM to say — it isn't an
    error. If `bias` is `NEUTRAL`, the engine rejects with reason `"bias is
    NEUTRAL; no trade"` before touching anything else.
  </Step>
  <Step title="Conviction floor">
    Checked before any network I/O, because it's free.
    `signal.conviction >= MIN_CONVICTION` (0.30). This is also why the
    orchestrator's system prompt asks Claude to calibrate conviction
    honestly — a model that always answers 0.9 makes this gate meaningless,
    and a model handed five kinds of context instead of one has more ways to
    talk itself into a high number. The prompt is explicit that conviction
    must *fall* when dimensions disagree; see
    [Market Context](/orchestrator/market-context).
  </Step>
  <Step title="Fetch account state">
    `broker.get_equity()` and `broker.get_open_positions()`. First real
    network call in the path.
  </Step>
  <Step title="Position-count limit">
    Only applies when the signal would open a **new** ticker.
    `len(positions) < MAX_OPEN_POSITIONS` (40). Adding to an existing
    position never trips this gate.
  </Step>
  <Step title="No flipping an existing position">
    If you already hold a long position in this ticker and a `BEARISH`
    signal comes in, it's rejected rather than silently flipped to short.
    There's no "close and reverse" logic — that's a deliberate scope limit,
    see [Next Steps](/next-steps).
  </Step>
  <Step title="Market data: price and volatility">
    `market_data.get_latest_price()` and `get_atr()`. Then
    `check_atr_sanity()` — if ATR is below 0.2% of price, the data is
    treated as too degenerate to place a meaningful stop against, and the
    signal is rejected.
  </Step>
  <Step title="Calculate the stop-loss">
    `risk_engine.calculate_stop_price()` — entry ± `ATR_STOP_MULTIPLIER`
    (2.0) × ATR, direction depending on side.
  </Step>
  <Step title="Size the position">
    `risk_engine.calculate_position_size()`, existing exposure in this
    ticker included. If the result is below `MIN_ORDER_QTY` (1) — no room
    left under the 5% cap — reject with the specific numbers (equity,
    price, existing exposure) in the reason.
  </Step>
  <Step title="Submit">
    `broker.submit_bracket_order()`. This is the only step with side
    effects on the broker; every prior step is pure computation or a
    read-only fetch. It carries a `client_order_id` that is stable for this
    ticker, side and heartbeat window, so re-running the step cannot open a
    second position — see below.
  </Step>
</Steps>

## The one step that can happen twice

Every step before the submit is a pure computation or a read-only fetch, so
re-running it is free. The submit is not: if Alpaca accepts the order and the
response is lost in transit, the caller sees a failure for an order that
actually exists. The next cycle would then produce the same signal and open a
second position — one that was never sized against the 5% cap, because the cap
was checked against the first order alone.

`build_client_order_id()` closes that by deriving the id from the decision
rather than from chance:

```python
window = int(moment.timestamp()) // IDEMPOTENCY_WINDOW_SECONDS
return f"{ticker.upper()}-{side.lower()}-{window}"
```

A random id per call would give no protection at all — the retry would simply
carry a different one. Because this id is stable, the second submission is a
duplicate Alpaca refuses.

<Note>
  The window is `HEARTBEAT_INTERVAL_MINUTES`, not a hard-coded hour, so
  changing the cadence moves the suppression window with it.
</Note>

<Warning>
  **The trade-off, stated plainly:** a genuine second entry for the same ticker
  and side inside one window is also refused. At the default daily cadence the
  pipeline produces at most one signal per ticker per cycle, so it should not
  arise — and when the alternative is doubling a position, refusing a real
  order is the safe direction to fail.
</Warning>

A refused duplicate raises `DuplicateOrderError`, and the engine reports it as
**`REJECTED`, not `ERROR`**. The order exists; the guardrail worked. Calling it
an error would invite exactly the retry the id was added to defuse, and would
inflate the audit log's error rate with a mechanism doing its job.

<Note>
  Alpaca's exact wording for a duplicate `client_order_id` could not be
  verified from the environment this was built in, so the match on its error
  message is deliberately broad and **fails toward a plain `BrokerError`** — an
  unrecognised message is reported as an ordinary submit failure rather than
  being swallowed as a benign duplicate. Check the first live duplicate in
  `logs/execution_audit.log` to confirm it is classified as `REJECTED`.
</Note>

## Reading the code directly

```python
def _execute(self, signal: LLMSignal) -> ExecutionResult:
    side = _SIDE_FOR_BIAS.get(signal.bias)
    if side is None:
        return reject("bias is NEUTRAL; no trade")

    if not risk_engine.check_conviction_threshold(signal.conviction):
        return reject(f"conviction {signal.conviction:.2f} below minimum {cfg.MIN_CONVICTION:.2f}")

    equity = self._broker.get_equity()
    positions = self._broker.get_open_positions()
    existing = next((p for p in positions if p.ticker == signal.ticker), None)

    if existing is None and not risk_engine.check_position_count_limit(len(positions)):
        return reject(f"already holding {len(positions)} positions (max {cfg.MAX_OPEN_POSITIONS})")

    if existing is not None and existing.side != side:
        return reject(f"conflicting open {existing.side} position of {existing.qty:g} shares")

    price = self._market_data.get_latest_price(signal.ticker)
    atr = self._market_data.get_atr(signal.ticker)
    if not risk_engine.check_atr_sanity(atr, price):
        return reject(f"ATR {atr:.4f} is below {cfg.MIN_ATR_PCT_OF_PRICE:.2%} of price {price:.2f}", ...)

    stop_price = risk_engine.calculate_stop_price(price, atr, side)

    existing_value = existing.market_value if existing else 0.0
    qty = risk_engine.calculate_position_size(equity=equity, price=price, existing_position_value=existing_value)
    if qty < cfg.MIN_ORDER_QTY:
        return reject(f"no room under {cfg.MAX_POSITION_PCT:.0%} cap: ...", ...)

    order = self._broker.submit_bracket_order(ticker=signal.ticker, qty=qty, side=side, stop_price=stop_price)
    return self._result(signal, ExecutionStatus.ACCEPTED, ..., order_id=order.order_id)
```

## Nothing ever raises

`execute()` — the public method `app/main.py` calls — wraps all of this:

```python
def execute(self, signal: LLMSignal) -> ExecutionResult:
    try:
        result = self._execute(signal)
    except (BrokerError, MarketDataError, risk_engine.RiskViolation) as exc:
        result = self._result(signal, ExecutionStatus.ERROR, f"{type(exc).__name__}: {exc}")
    except Exception as exc:
        log.exception("unexpected error while executing %s", signal.ticker)
        result = self._result(signal, ExecutionStatus.ERROR, f"unexpected {type(exc).__name__}: {exc}")

    log_execution(signal, result)
    return result
```

<Check>
  Every code path — including a genuinely unexpected bug — ends in a
  logged `ExecutionResult`, never an unhandled exception reaching the HTTP
  layer. The webhook can return a 500 on a wire-level problem (bad JSON),
  but never because the risk engine itself blew up.
</Check>

## The three outcomes

| Status | Means | Example reason |
|---|---|---|
| `ACCEPTED` | Order submitted with a stop-loss attached | `"submitted buy 50 AAPL @ ~189.20, stop 185.10"` |
| `REJECTED` | A guardrail said no; nothing was submitted | `"conviction 0.25 below minimum 0.30"` |
| `ERROR` | Broker, market data, or risk math raised | `"BrokerError: insufficient buying power"` |

Every one of these — accepted, rejected, or errored — is written to
`logs/execution_audit.log` as a single JSON line pairing the original
signal with the result.
