This system is complete for what it set out to do: keep an LLM's output
structurally incapable of controlling a trade. It is not a finished trading
product. These are the honest gaps.

<CardGroup cols={2}>
  <Card title="Webhook auth is a shared secret" icon="key">
    Fine for one orchestrator you control talking to one engine you
    control. Swap for HMAC request signing before exposing this to anything
    less trusted.
  </Card>
  <Card title="No exit path besides the stop" icon="arrow-right-from-bracket">
    The engine has no close-or-reduce logic. A position's only exit is the
    stop-loss attached at entry. A signal opposing an existing position is
    rejected rather than flipping it — see [Decision Path](/decision-path).
  </Card>
  <Card title="Scoring measures the signal, not the P&L" icon="gauge">
    [Scoring the Journal](/scoring) answers whether conviction predicted the
    move — but from close-to-close returns that ignore the stop-loss, slippage
    and commission. A call that was right about direction and stopped out on
    the way there still scores as a win. The join it needs now exists: the
    `decisions` view in [The Archive](/database) carries the size, entry and
    stop the engine actually chose. What is left is teaching the scorer to use
    it — walking each filled trade forward bar by bar and asking whether the
    stop was hit first.
  </Card>
  <Card title="Nothing acts on the scores" icon="robot">
    If the report says a dimension carries no information, or that the
    conviction floor is filtering the wrong way, changing the prompt or the
    threshold is a manual decision. That is the right default until there are
    months rather than weeks of data behind it — but it does mean the loop is
    not closed.
  </Card>
  <Card title="Git still carries the journal" icon="database">
    [The Archive](/database) now indexes both logs into SQLite *and* pushes
    them to Postgres — but the heartbeat still commits the JSON-lines files
    back to the repository, because they remain the record and the runner is
    discarded. Once the remote has run long enough to be trusted, the commit
    step could rotate or stop, and that is the change that actually stops git
    growing. Not before: a remote you have never restored from is not a backup.
  </Card>
  <Card title="Insider data is only as good as yfinance's copy of it" icon="user-secret">
    [Insider activity](/orchestrator/insiders) comes from Yahoo's rendering of
    Form 4 filings, not from the filings themselves. It can lag, and it can
    miss. SEC EDGAR is the authoritative source and needs no API key either —
    just CIK mapping and XML parsing. Worth building only once
    [the scorer](/scoring) shows the dimension carries signal.
  </Card>
  <Card title="The exposure caps see one broker" icon="layer-group">
    `execution_engine.py` asks a single broker for equity and open positions,
    so the group and sleeve caps bound one book. That is correct today and
    breaks the day a position can live at a second broker — not by raising,
    but by silently under-counting: the same holding split across two accounts
    passes a cap that the combined position would fail. The seam to fix it is
    already there, and [The Portfolio View](/portfolio-view) says what to build
    and when.
  </Card>
  <Card title="A total context failure leaves no trace" icon="ghost">
    When news cannot be fetched, the ticker is skipped before a
    `TickerContext` exists — and `journal.record` needs one, so nothing is
    written. Every other failure path journals its error. The cycle summary and
    the [exit code](/deployment) now make a whole-cycle outage
    loud, but the journal itself still has no row for "never got started",
    which is a hole in the claim that it records everything the model saw.
  </Card>
  <Card title="Context is fetched serially" icon="hourglass">
    `context.py` fetches each source one after another, and the sources are
    independent. On the default three-ticker watchlist nobody notices; on a
    longer one this becomes the slowest part of a cycle.
  </Card>
</CardGroup>

## If you want to go further

<Steps>
  <Step title="Wire up HMAC signing">
    Replace the `x-webhook-secret` header check in `app/main.py` with a
    signature over the request body.
  </Step>
  <Step title="Add a close/reduce path">
    A new method on `broker_client.py` and a new decision branch in
    `execution_engine.py` — deliberately scoped out of the initial build so
    the guardrail surface stayed small enough to fully test.
  </Step>
  <Step title="Run the scorer for long enough to believe it">
    [Scoring the Journal](/scoring) already answers the questions the journal
    was built for, and marks anything under 20 observations as `too few`. The
    work left is patience: a three-ticker watchlist produces a few signals a
    day, so the numbers only become evidence after weeks, not days. Resist
    tuning the prompt against a sample the report is telling you not to trust.
  </Step>
  <Step title="Score filled trades, not just directions">
    The `decisions` view in [The Archive](/database) joins each signal to the
    order it became, so `analysis/returns.py` can stop assuming a position is
    held for the whole horizon and start checking whether the stop was hit
    first. That is the difference between "was the model right" and "did this
    make money", and only the second one is the question.
  </Step>
  <Step title="Aggregate the book before adding a second broker">
    `BrokerClient` is already a Protocol and the risk engine already takes
    "anything with `.ticker` and `.market_value`", so this is a merge layer
    rather than a redesign — but it has to ship *with* the second broker, not
    after it, because until it exists the exposure caps under-count. Settle the
    accounting currency at the same time: every cap is a percentage of
    `get_equity()`, and that number stops being unambiguous once an account can
    hold shekels. See [The Portfolio View](/portfolio-view).
  </Step>
  <Step title="Go to EDGAR for insider data, if it earns it">
    [Insider activity](/orchestrator/insiders) ships against yfinance, which
    needed no API key after all. The authoritative source is SEC EDGAR — the
    Form 4 filings themselves, free, needing only a User-Agent header — at the
    cost of CIK mapping and XML parsing.

    Do not build it on principle. Run the current version, then check whether
    `insider_score` correlates with anything in [the scorer](/scoring). A
    better feed for a dimension that carries no signal is wasted work.
  </Step>
  <Step title="Fetch the context sources concurrently">
    `context.py` fetches price history, fundamentals, the calendar,
    recommendations, upgrades, holders and insider filings one at a time. They are
    independent, and the degradation model already treats each failure
    separately, so a thread pool would shorten a cycle without changing the
    semantics. Worth doing before the watchlist grows, not after.
  </Step>
  <Step title="Widen the watchlist thoughtfully">
    Each ticker is one Bright Data request and one Claude call per cycle —
    check both providers' usage pages before scaling `WATCHLIST` up
    significantly. The yfinance enrichment costs nothing per request, but it
    is rate-limited and unauthenticated, which is why the slow-moving parts
    are cached for six hours.
  </Step>
</Steps>

## Going live (don't, yet — but here's what it takes)

`TradingClient(..., paper=True)` is a hard-coded literal in
`app/broker_client.py`, and a CI job fails the build if that stops being
true. Removing that safety is an explicit, reviewable code change — not a
setting, not an environment variable. See [Guardrails](/guardrails) for why
that design choice was made deliberately.
