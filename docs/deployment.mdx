title: "Deployment"
description: "Running the heartbeat without a server, a webhook, or a laptop left open"
---

The system needs to run one cycle per trading day, after the US open. That is an
awkward shape for a phone and overkill for a VM, so the default target is a
**scheduled GitHub Actions job**: no server, no open port, and the logs are
readable from the GitHub mobile app.

## Two things had to change first

<Steps>
  <Step title="The webhook became optional">
    The orchestrator used to POST signals to a separately running FastAPI app.
    A scheduled job has nothing to POST *to*, so `EXECUTION_MODE=direct` runs
    the engine in the same process instead.
  </Step>
  <Step title="The cycle learned when the market is shut">
    The scheduler ran every 60 minutes regardless, so roughly two thirds of
    cycles spent a Bright Data request and a model call per ticker on a closed
    market — and submitted orders into it.
  </Step>
</Steps>

## Direct mode is a transport change, not a safety change

The boundary that keeps the model away from order parameters is
`LLMSignal(extra="forbid")` plus the engine owning all sizing and stops. That
lives in the schema, not in the network hop.

| | Webhook mode | Direct mode |
|---|---|---|
| Smuggled `quantity` field | HTTP 422 | `ValidationError` |
| Who sizes the position | Engine | Engine |
| Who sets the stop | Engine | Engine |
| `WEBHOOK_SHARED_SECRET` | Required | **Never read** |
| Processes to run | 2 | 1 |

<Warning>
  **The one thing that genuinely weakens.** In direct mode the orchestrator
  process holds Alpaca credentials, so "broker credentials never share a
  process with LLM-adjacent code" becomes "never share a *module*" — still
  enforced by CI, but by module boundary rather than process boundary.

  The practical exposure is unchanged: the model's output is a closed schema
  and cannot reach code execution. But it is a real difference, and it is why
  `webhook` mode still exists rather than having been deleted. Keep it if you
  want the engine on a different machine from the LLM side.
</Warning>

## Market hours are checked twice, on purpose

```python
# app/execution_engine.py — step 2, before any market-data fetch
if not self._broker.is_market_open():
    return reject("market is closed")
```

The **engine gate** is the safety property: a signal replayed by hand, or
delivered late by a webhook retry, must not open a position into a closed
session. The **cycle gate** in `run_cycle()` is the cost property: it asks the
same question before any news fetch or model call, which is where a
closed-market cycle actually spends money.

<Note>
  The authority is Alpaca's own clock, not a local weekday-and-time
  calculation. A hand-rolled check would have to carry the exchange holiday
  calendar, the half-day schedule, and the fact that US market hours move
  against UTC on a DST schedule that is not Europe's. Getting any of those
  wrong means trading into a closed market or skipping a real session.
</Note>

<Warning>
  An unreadable clock does **not** halt trading. It is logged and the cycle
  continues, because one flaky API call silently stopping the system is worse
  than a wasted cycle — and the engine re-checks anyway.
</Warning>

### The one path with no clock to ask

The pre-market cycle (`--premarket`, made to wait on the Batch API before the
open — see [cost](/cost#half-price-for-waiting)) starts before the market can
possibly be open, so asking Alpaca's clock would refuse every run. There is a
third gate for exactly that path: `config/market_calendar.py`'s
`is_trading_day`, a version-controlled list of full-day NYSE closures checked
before anything is fetched.

It is deliberately narrower than the authority it stands in for. It knows
weekday and listed holiday, and nothing else — a half day passes it, because
the market genuinely trades then, and an unscheduled closure isn't in it at
all. Both of those still reach the broker's own gate downstream, which is
still what refuses the orders. The list needs a year added as each one
approaches; a year with no entries doesn't stop the cycle, it just logs that
it's guessing and defaults to running — the same wasted-cycle cost paying for
a batch bought before this gate existed at all, not a missed session.

<Note>
  Since 25 Sep 2026 the scheduled workflow no longer uses this path. The full
  model has been asked live since 23 Sep, so a pre-market start would send its
  orders into a closed market, where the engine refuses them and the profit
  ladder is skipped. The cycle now starts after the open with plain `--once`,
  which keeps Alpaca's clock as the gate. The flag still exists in
  `orchestrator/heartbeat.py`; the calendar check still runs on every batched
  cycle.
</Note>

## Setting up the scheduled job

<Steps>
  <Step title="Add your secrets">
    Repository **Settings → Secrets and variables → Actions**. Add as
    *secrets*: `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, `ANTHROPIC_API_KEY`,
    `BRIGHTDATA_API_TOKEN`. Add as *variables*: `BRIGHTDATA_UNLOCKER_ZONE`
    (`cli_unlocker` if you used `brightdata login`) and `WATCHLIST`.

    Four more secrets are optional and free: `FRED_API_KEY`, `EIA_API_KEY`,
    `USDA_NASS_KEY` and `FINNHUB_API_KEY`. Each one adds a section to the
    prompt and none of them is depended on — with a key absent that section
    is simply not there. See [Official Data](/orchestrator/official-data).
  </Step>
  <Step title="Run it once by hand">
    **Actions → heartbeat → Run workflow.** This is the smoke test that
    matters: the yfinance and Bright Data parsers were only ever validated
    against mocks, so watch this run's log for `context gaps` warnings or
    empty headlines. See [Testing](/testing).
  </Step>
  <Step title="Let the schedule take over">
    Two crons, both on weekdays, and the job exits immediately when Alpaca
    says the market is shut:

    | cron (UTC) | what it is |
    | --- | --- |
    | `40 14 * * 1-5` | the cycle, once a day: 10:40 New York in summer, 09:40 in winter |
    | `35 17 * * 1-5` | the catch-up, which usually does nothing |

    The second one exists because the first can simply not fire — see below.
    Neither is trusted to be on time: see
    [If GitHub skips or delays the run](#if-github-skips-or-delays-the-run).
  </Step>
</Steps>

## Two things that make a missed run survivable

<Warning>
  **GitHub Actions cron is best-effort.** Runs can be delayed 5–15 minutes or
  more under load, silently skipped under heavy load, and scheduled workflows
  are disabled automatically after 60 days without repository activity. If you
  want punctual, guaranteed execution, run `python -m orchestrator.heartbeat`
  (no `--once`) on a small always-on host instead — the same direct mode works
  there.
</Warning>

### The catch-up run

A skipped 14:40 costs the whole day: no signals, no journal line, and a gap
in the history the blend is fitted on. So a second schedule runs about three
hours later. Like every cycle run, it asks one question first — *may this run
start a cycle?*

```bash
python analysis/cycle_day.py --journal logs/signal_journal.log --decide   # run, already or too_late
```

It reads the journal's own timestamps and, in the workflow, GitHub's record
of today's other heartbeat runs (`--runs`, `--jobs`; see
[below](#if-github-skips-or-delays-the-run)), and prints one word:

| answer | meaning |
| --- | --- |
| `run` | no cycle is journalled for today, no other run today reached its trading step, and there is still time |
| `already` | a cycle is journalled for today, or another run today reached "Run one cycle" after the open (whatever its result); this run stops |
| `too_late` | neither, but it is past 14:30 New York (11:30 on a half day); this run stops |

The reason goes to the job summary: which run stopped this one, or that
GitHub could not be read and the answer rests on the journal alone.

It **always exits 0**: a non-zero exit would be indistinguishable from the
script itself breaking, and "the guard crashed" must not read as "no cycle
ran". Every later step is conditional on the guard not saying skip, including
the ones that would otherwise run on failure. (Without `--decide` it still
prints the old `yes` or `no`.)

14:30 New York is the latest safe start because the runs of 21-24 Sep took
26 to 74 minutes, and orders go out along the way. A cycle started later could
still be sending orders at the 16:00 close, where the engine refuses them and
the profit ladder is skipped. On a half day (the day after Thanksgiving, and
Christmas Eve when it is a weekday) the market closes at 13:00, and the latest
safe start is 11:30; the half days are listed in `analysis/cycle_day.py` as
`EARLY_CLOSES`.

What makes a re-run safe for entries is not the guard — it is the broker.
Every order carries a client order id derived from the ticker, the side and
the current day, so if the first run *did* place an order and the guard were
somehow wrong, Alpaca rejects the duplicate rather than doubling the position.
See [Position Management](/position-management). The profit ladder has no such
id: it counts the rungs a position has already sold from the audit log, so a
run whose audit log never reached the branch could have its rungs sold a
second time. That is why the guard does not trust the journal alone, and why
the watchdog below never re-runs a day on its own after a run that reached
its trading step.

## If GitHub skips or delays the run

GitHub's cron has been much worse here than "a few minutes late". In the week
of 21 Sep the old 12:35 UTC cron arrived 4.5 to 5.7 hours late every day, and
the 17:35 one about 3 hours late. On 16 Sep a cron never arrived at all. So
the daily run has three ways to start, and a guard that lets only one of them
trade:

<Steps>
  <Step title="The schedule">
    The two crons above. On a good day the 14:40 cron starts the cycle and
    nothing else is needed.
  </Step>
  <Step title="The watchdog">
    `heartbeat-watchdog.yml` checks at 15:10, 15:40, 16:40 and 17:40 UTC. It
    reads the journal and GitHub's list of today's runs
    (`analysis/watchdog.py` makes the decision; the workflow only acts on it):

    | what it finds | what it does |
    | --- | --- |
    | not a trading day, or before 15:10 UTC | nothing |
    | a cycle already in the journal, or a run on its way | nothing |
    | a run waiting over 30 minutes for a GitHub machine | tells your phone; starts nothing |
    | the backup already started twice today, still no cycle | tells your phone; stops trying |
    | a run today that reached its trading step, whatever its result, and no cycle in the journal | tells your phone urgently that it may have traded; starts nothing |
    | no cycle, and 14:15 New York or later (11:15 on a half day) | tells your phone that there is no trading today |
    | no cycle and no run, earlier than that | **starts the run as the backup** and tells your phone |

    The backup stops 15 minutes before the 14:30 latest safe start because
    that is about how long GitHub can take to bring a dispatched run to its
    guard, which asks "too late?" again when it gets there. If a backup still
    arrives too late, heartbeat.yml tells your phone so, rather than leaving
    "the backup has started it" as the last word.

    A run that reached "Run one cycle" may have placed orders whose record
    never reached the branch (a refused push, a lost machine). A green one
    with nothing in the journal most likely ran on another branch, but
    nothing automatic can tell those apart, and the guard stops every later
    cycle that day on the same evidence. So the watchdog reads the steps of
    every finished run from GitHub, every attempt of it, and starts a backup
    only when none got that far. Otherwise, check the run and the account
    and, if it placed nothing, start heartbeat by hand with `rerun` ticked.
    A "Run one cycle" that was over before the 09:30 open does not count: it
    found the market shut and placed nothing.

    The phone message gives times in UTC and in Israel time. The watchdog's
    own crons can be late too, for the same reason, so it can also be started
    by a dispatch (next step).
  </Step>
  <Step title="The Claude Routines">
    Routines in the owner's Claude account dispatch workflows at fixed times.
    A dispatched run is created the moment it is asked for; it does not wait
    in GitHub's cron queue. That is what makes "within 30 minutes" real:
    a Routine that dispatches `heartbeat-watchdog.yml` just after 15:10 UTC.
  </Step>
</Steps>

All of these can fire on the same day. The guarantee: **on one trading day,
only one run reaches "Run one cycle" after the open, and the only way a
second one can is a person dispatching heartbeat with `rerun`.** A run that
is over before the open found the market shut and placed nothing, so it
neither counts nor stops the day's cycle. Path by path:

| what starts the run | what stops a second cycle |
| --- | --- |
| the 14:40 cron, on time or hours late | the guard |
| the 17:35 catch-up cron | the guard |
| the watchdog's backup | the watchdog, which starts none on a day the guard would stop; then the guard. It never sends `rerun` |
| a Claude Routine | the guard |
| a person, Run workflow without `rerun` | the guard |
| a person, "Re-run" on a run's page | the guard, which also counts that run's own earlier attempts, even on a run dispatched with `rerun` |
| a protection pass | nothing to stop: it never runs "Run one cycle", so it never stops a cycle either |
| **a person, Run workflow with `rerun`** | **nothing: the one way past the guard** |

The guard stops a cycle for either of two reasons:

- **The journal already has today.** The workflow checks out the branch's
  latest commit, not the commit the run was created on, so a run that waited
  behind a running cycle sees that cycle's journal.
- **GitHub's record shows another run today reached "Run one cycle"**,
  whatever its result, or an earlier attempt of this run did. This is the
  run the journal cannot show: one that traded and whose commit never
  reached the branch (a refused push, a lost machine). The broker refuses a
  second entry for the same ticker, side and UTC day, but the profit ladder
  counts the rungs it has sold from the audit log, which was lost with the
  journal, so a second cycle could sell them again. Until 25 Sep only the
  watchdog looked for that run, and a late catch-up cron or a Routine passed
  the guard on such a day. A run on another branch looks the same from
  here, and counts the same: the watchdog tells your phone, and you decide.
  Whatever the run's status: a run that traded and is re-run from its page
  waits as "pending" again, and still counts. A "Run one cycle" that began
  and ended before the 09:30 New York open does not: the engine and the
  profit ladder both refuse to act while the market is shut, so it placed
  nothing, and counting it would let a pre-market dispatch close the day.

And **runs never overlap**: the `heartbeat` concurrency group runs one at a
time, so no two guards decide at once.

**"Re-run" on a run dispatched with `rerun`** is guarded too. A re-run
replays the dispatch, inputs included, so it still carries `rerun`, which
was given for the first attempt, not for trading the day again. On a second
or later attempt the guard runs anyway and asks one question: did an
earlier attempt of this run reach "Run one cycle"? If it did, or GitHub
cannot say, the run stops; to run another cycle, start heartbeat by hand
with `rerun` ticked. A run dispatched with `rerun` on an earlier day and
re-run today is guarded like any other run: its `rerun` was for that day.

The guarantee needs two things to hold:

- **GitHub answers when the guard asks.** If the list of runs, or one run's
  steps, cannot be read (or takes more than 30 seconds), the guard never
  fails the run for it. It decides from the journal alone, as it did before
  25 Sep, and the job summary says so; on that day, a run that traded and
  lost its record would not be seen. The watchdog errs the other way: a run
  whose steps it cannot read counts as one that traded. So does the guard
  of a re-run of a `rerun` run, which stops.
- **The run was created today.** Runs are counted on the New York day they
  were created, so a run from an earlier day, re-run today from its page, is
  seen by later runs only through the journal. Use `rerun` instead.

The journal push is also tried three times, five seconds apart, so a lost
record is rarer to begin with: most refusals are something else pushing to
the branch in between, or a dropped connection, and a fresh pull and push a
moment later gets through.

From the first heartbeat cycle after this change, each journal line the
cycle writes also says what started its run: a `run` block with the trigger
(`schedule`, `backup`, or `manual` for any other dispatch, a person's or a
Claude Routine's), when the day's run was due, when this one started, how
many minutes late, and the GitHub run id. The daily report shows it in one
line. Lines from a local run carry no block.

### The job's ceiling

The job's `timeout-minutes` is 180, raised from 45 and then from 90. The cycle
asked the Batch API for eighty tickers and waited; a busy batch can take well
over an hour, and the old ceiling killed the job mid-wait — losing the run
*and* the batch results that had already been paid for. The collector has its own, shorter
deadline inside that ceiling, so it gives up first and prints a batch id the
run can be resumed from. Two clocks, deliberately: the outer one is a
backstop, the inner one is the one that produces something useful.

## A cycle that reaches nothing fails the run

The first scheduled cycle ran with every secret unset. It failed all 35 tickers
on the missing Bright Data token, wrote no journal line, committed nothing —
and exited 0. The run showed a green tick, which is the worst possible outcome:
a system that is not running, reporting that it is.

`--once` now exits **1** when a cycle attempted tickers and none of them reached
the engine. That is the condition, and the wording matters:

- **Not "no trade was placed."** A cycle where the engine rejected every signal
  did its job — [the conviction floor](/decision-path) filtering is the system
  working, not failing.
- **Not a closed market.** Nothing was attempted, so there is nothing to report.
- **Not an empty watchlist.** That is a configuration choice.

What it catches is a cycle where nothing the model produced ever got far enough
to be judged — which leaves no trade, no journal line, and nothing to score
later.

<Note>
  Deliberately not configurable. A switch to make this advisory would repeat
  the mistake the `continue-on-error` on the ticker check made: the one signal
  whose entire job is to be loud, made quiet for convenience. See
  [Continuous Integration](/continuous-integration).
</Note>

Both the commit and the Supabase push run under `if: always()`, so a failed
cycle still saves whatever it did write. A ticker that reached the model and was
refused there *is* journalled with its error, and those are exactly the lines
worth having when a run is red.

### The job summary

Every cycle appends a summary to the GitHub job page — verdict counts when it
worked, and when it did not, the stage every ticker died at plus which
credential to suspect:

```
## Heartbeat cycle

### Nothing reached the engine

All **35** tickers stopped before a signal could be judged.

| Stopped at | Tickers |
| --- | --- |
| context never gathered | 35 |
```

It is rendered in Python (`render_summary`) rather than in workflow YAML, for
the same reason the Supabase push decides its own no-op in Python: a summary
that exists only as a shell expression is covered by nothing except a green
run, and the whole point of it is to be read when the run is not green.

## Why the journal is committed back

The runner is discarded after each job, so an uncommitted journal is a lost
cycle — and the journal is the only record of what the model saw before it
decided. Committing it rather than uploading an artifact means the scorer can
read the whole history from a plain clone, artifacts cannot expire out from
under you, and you can read your own trading history on a phone.

The cost is roughly seven commits a trading day on `main`. If that becomes
noisy, point the workflow at a `journal` branch instead.

## Running it locally

```bash
python -m orchestrator.heartbeat --once   # one cycle, then exit
python -m orchestrator.heartbeat          # schedule every HEARTBEAT_INTERVAL_MINUTES
```
