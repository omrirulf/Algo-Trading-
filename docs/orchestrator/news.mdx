`orchestrator/news.py` fetches the past 24 hours of Google News results for
`"<TICKER> stock"` through [Bright Data's SERP API](https://brightdata.com/products/serp-api),
and returns up to 10 de-duplicated headline lines.

## Setup

<Steps>
  <Step title="Authenticate — CLI or dashboard">
    Run `brightdata login` (the official CLI's browser OAuth flow; `--device`
    when headless) and leave `BRIGHTDATA_API_TOKEN` blank, or copy a token
    from *Account settings → API tokens* into it. Resolution order is
    `BRIGHTDATA_API_TOKEN` → `BRIGHTDATA_API_KEY` → the CLI's stored login.
  </Step>
  <Step title="Point at a zone">
    Set `BRIGHTDATA_SERP_ZONE` to a **SERP API** zone if you have one. If you
    only ran `brightdata login`, set `BRIGHTDATA_UNLOCKER_ZONE=cli_unlocker`
    instead — the zone the login already created. Either works; see below.
  </Step>
</Steps>

## A Web Unlocker zone is enough

`brightdata login` provisions `cli_unlocker` and `cli_browser`, not a SERP API
zone — so the obvious reading is that you must still create one in the
dashboard. **You don't.** Bright Data's own CLI sends search queries through
an unlocker zone, and prefers to:

```ts
// brightdata/cli — src/commands/search.ts
const zone = resolve(opts.zone, 'BRIGHTDATA_SERP_ZONE', 'default_zone_serp')
    ?? resolve(opts.zone, 'BRIGHTDATA_UNLOCKER_ZONE', 'default_zone_unlocker');
...
const body = {zone, url: search_url, format: 'raw'};   // with brd_json=1
```

Its `init` command goes further and offers the unlocker zone as the SERP
default with *yes* preselected, falling back to `cli_unlocker` when nothing
else is configured. The request body above is byte-for-byte the shape this
module sends.

`orchestrator/news.py` mirrors that resolution, so a machine set up for the
CLI needs nothing else:

```python
def resolve_zone(serp_zone: str = "") -> str:
    return serp_zone.strip() or os.environ.get(CLI_UNLOCKER_ENV_VAR, "").strip()
```

<Note>
  Net effect: **Bright Data needs no dashboard visit at all.** `brightdata
  login` plus `BRIGHTDATA_UNLOCKER_ZONE=cli_unlocker` is a complete setup.
</Note>

<Warning>
  This was read from the CLI's source, not confirmed against a live call —
  Bright Data's API is unreachable from the environment this was built in. If
  an unlocker zone turns out to be refused for search on your account, the
  symptom is the `NewsFetchError` about HTML below, and the fix is a SERP API
  zone in the dashboard with `BRIGHTDATA_SERP_ZONE` set. Nothing else changes.
</Warning>

<Note>
  One request per ticker per cycle. The default three-ticker watchlist is
  35 requests/day at the default daily cadence — comfortably inside Bright
  Data's free tier / pay-as-you-go pricing, but check your zone's usage page
  after the first day if you widen the watchlist.
</Note>

## The request

```python
BRIGHTDATA_REQUEST_URL = "https://api.brightdata.com/request"

def build_news_search_url(ticker: str) -> str:
    params = {
        "q": f"{ticker} stock", "tbm": "nws", "tbs": f"qdr:{NEWS_LOOKBACK}",  # qdr:d = past 24h
        "num": MAX_HEADLINES, "hl": "en", "gl": "us", "brd_json": 1,
    }
    return f"https://www.google.com/search?{urlencode(params)}"
```

`brd_json=1` is what tells Bright Data to return parsed JSON instead of raw
HTML. The request body sent to Bright Data itself is deliberately small:

```python
body = {"zone": self._zone, "url": build_news_search_url(ticker), "format": "raw", "country": BRD_COUNTRY}
headers = {"Authorization": f"Bearer {self._token}", "Content-Type": "application/json"}
```

This shape — `POST /request` with `{zone, url, format}` and a Bearer token —
comes from Bright Data's own Python SDK and MCP server, since their public
docs site wasn't reachable from the environment this was built in.

## The request exits from the US

`"country": "us"` (`BRD_COUNTRY`) asks Bright Data to send the search from a
US exit. Without it, a share of the answers since late September 2026 were a
200 with an empty body (6 Oct: 22 names without news; 15 Oct: 55), and Bright
Data's own headers on every one of them said `x-brd-status-code 502;
x-brd-error redirect location was rejected`: Google answered the search with a
redirect, most likely its consent or regional page for a non-US exit, and the
Unlocker refused to follow it. A SERP API zone showed the same (6 of 20 empty
against 4 of 20), so the zone was not the lever; the same request from a US
exit came back empty 2 times of 20 against 5 of 20 without it
(`replay/serp_zone_probe.py`, 16 Oct 2026). The owner's decision of 17 Oct
2026. The search URL, the zone, the parser and the prompt are unchanged; the
shadow universe's search (`orchestrator/universe_news.py`) shares the request,
and the article-text fetch (`orchestrator/article_text.py`) sets no exit.

## Parsing: tolerant on purpose

`parse_news_results()` doesn't assume one fixed response shape. It:

<CardGroup cols={2}>
  <Card title="Unwraps two response shapes" icon="layer-group">
    Accepts either the bare parsed JSON, or Bright Data's
    `{status_code, headers, body}` wrapper — recursing into `body` when
    present, and surfacing a non-2xx inner status as an error.
  </Card>
  <Card title="Falls back across result keys" icon="list-check">
    Looks for `news`, then `top_stories`, then `organic` — the same query
    can come back shaped as a news tab result or a regular SERP.
  </Card>
  <Card title="De-duplicates by title" icon="copy">
    Case-insensitive dedup, since the same story often appears from
    multiple outlets.
  </Card>
  <Card title="Caps at 10 headlines" icon="hashtag">
    `MAX_HEADLINES = 10` — enough signal for the LLM without ballooning the
    prompt.
  </Card>
</CardGroup>

Each surviving headline is formatted as:

```
<title> — <snippet> (<source>, <when>)
```

## Failure modes: `NewsFetchError`

Every way this can go wrong — HTML instead of JSON (usually means the zone
isn't a SERP API zone, or `brd_json=1` didn't take), a non-JSON body, a
non-2xx response, a transport error, or a missing token/zone at
construction time — raises `NewsFetchError`. `heartbeat.py` catches this per
ticker and logs it; one ticker's bad response never stops the cycle.

Two of those get one more try. A transport error (a timed-out read, a
dropped connection) is asked again after 2 seconds
(`RETRY_PAUSE_SECONDS`). A 200 whose body the parser refuses — most often an
empty body, which Bright Data sends in bursts (60 of 80 first answers on
15 Oct 2026) — is asked again after 10 seconds (`EMPTY_RETRY_PAUSE_SECONDS`;
the owner's decision of 16 Oct 2026, up from 2), and when the second answer
is refused too, the error carries Bright Data's own status headers
(`x-brd-status-code`, `x-brd-err-msg` and their kin, `BRD_HEADERS`) so the
journal says what the vendor said: `Bright Data returned an empty body with
its 200; nothing to parse (Bright Data said: x-brd-status-code 502)`. An HTTP
error is never retried.

<Note>
  Since 21 Sep 2026 a news failure no longer skips the ticker (issue #69):
  the context is assembled on its other sections, the NEWS section says
  "unavailable this cycle" rather than "none found", and the journal line
  carries a `news unavailable` gap that `analysis.health` counts. See
  [Market Context](/orchestrator/market-context). Since 5 Nov 2026 Bing's
  feed is asked first, below.
</Note>

Headlines are no longer the only thing in the prompt, either. They now sit
above four more sections — see
[Market Context](/orchestrator/market-context) for what else the model is
given and how it is told to weigh it.

<Warning>
  The exact field names inside a Bright Data news result (`title`,
  `description`/`snippet`, `source`/`source_name`, `date`/`time`) were read
  tolerantly because Bright Data's documentation site was unreachable while
  this was built. The parser was verified against a mocked transport only —
  check the log output on your first real cycle. If every ticker logs empty
  news, that's the first thing to look at.
</Warning>

## Bing's feed: the fallback when Google's answer is unusable

Since 5 Nov 2026 (the owner's decision of 4 Nov, after the probe of the
same day, `replay/bing_news_probe.py`; Amendments, 2026-11-05) a name whose
Google answer is unusable after the retries above — a second refused 200,
an HTTP error, a transport failure after its retry — is asked once more, of
Bing News: its RSS feed for the same query (`"<TICKER> stock"`, or `ETF`)
with Bing's past-24-hours filter (`build_bing_news_url`). The feed is
fetched directly first (no Bright Data, no token, a fraction of a second,
`BING_DIRECT_TIMEOUT_SECONDS`) and through Bright Data's zone only if the
direct fetch fails (`BrightDataNewsProvider._bing_fallback`).

The feed is read into the same `Headline` shape (`parse_bing_rss`) and then
**kept to the headlines that name the name** (`relevant_headlines`): the
ticker as a whole word, or for a company a distinctive word of its display
name (`Teva`, `Lilly`, `Exxon`; not `Bank` or `Royal` on their own,
`GENERIC_NAME_WORDS`). The probe showed why: with the filter on, Bing's feed
for a thin fund is mostly about other things (for DBA on 4 Nov: a country
music festival, a town's pool bond, a Senate race; one title in five named
the fund across the funds, against three in four for the companies).

A name with at least one headline left is judged on those, in the prompt's
unchanged NEWS section (the same `title — snippet (source, when)` lines,
`when` as `11h ago`), and its journal line says so: `context.news_note`
carries Google's reason, the route that answered and how many of the feed's
headlines named the name. A name with none left is handled as before the
fallback: "unavailable this cycle" in the prompt, a `news unavailable` gap
in the journal naming Google's reason and the feed's count, and
`analysis.health.news_gaps` counts it. `analysis.health.news_fallbacks`
warns when a tenth of the day's names took their news from the feed: the
cycle was whole, but Google, through Bright Data, was failing at a rate the
fallback was covering.

Bing is not the primary source. The model's input stays Google's wherever
Google answers, so the race's news input changes only on the names that
would otherwise have had none. The historical replay (`fetch_on`) and the
shadow universe's search (`orchestrator/universe_news.py`) have no fallback:
the feed has no window for a past day, and the universe's check measures
Google's coverage.
