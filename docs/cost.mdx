<Note>
Every figure on this page was measured while the cycle ran
`claude-haiku-4-5` screening into `claude-opus-5`. On 23 September 2026 the
full model became `openai/gpt-oss-120b` and the screen was switched off, so
these are the *old* bill: about $1.39 a cycle against roughly $0.20. They are
kept because the method is the point, and because the comparison is what
argued for the change.
</Note>

Cost used to be an estimate in this project: an assumed output length times a
list price. That estimate drove a real decision — how many tickers to watch —
which is the wrong way round. `response.usage` is now recorded on every call,
so the number in the journal is measured.

```json
"usage": {
  "model": "claude-opus-5",
  "input_tokens": 1420,
  "output_tokens": 1512,
  "cache_read_input_tokens": 0,
  "cost_usd": 0.0449
}
```

## Where the money goes

At this prompt shape — **~3,600 input tokens** against a thinking response —
**output is most of the bill**, because thinking tokens bill at the output
rate and output is several times input.

<Note>
  This page said ~1,400 tokens until 16 Sep. That was true before the nine
  enrichment sections were added; the prompt is now about 2.5× that, and every
  figure below was measured on the 16 Sep cycle rather than estimated.
</Note>

That ordering matters: **effort is a bigger lever than model tier.**

| | Lever | Effect |
|---|---|---|
| 1 | `USE_BATCH_API` | Halves every call that is not in a hurry — which here is all of them |
| 2 | `EFFORT` | Directly moves the 84% |
| 3 | Model tier | Multiplies both halves |
| 4 | The funnel (`SCREENING_ENABLED`) | Removes whole calls: the share of the watchlist the screen calls NEUTRAL |
| 5 | `SKIP_HELD_TICKERS` | Removes whole calls: the share of the watchlist already in the book |
| 6 | Watchlist length | Linear in calls |
| 7 | `HEARTBEAT_INTERVAL_MINUTES` | Linear in calls |
| 8 | Prompt caching | Only touches the 16% — and only when the breakpoint is placed correctly, see below |

## Half price, for waiting

The Message Batches API costs half of what the same request costs live. The
cycle is the ideal shape for it: eighty independent prompts, none of which
needs an answer in the same second.

What it costs is immediacy — a batch may take up to 24 hours, though a small
one usually finishes in minutes. Two things buy that back:

- **The cycle started pre-market.** Until 25 Sep 2026 a `12:35 UTC` cron
  gathered context, then waited on the batch in hours the strategy was not
  trading in anyway. Since 23 Sep the full model has been asked live, with no
  batch to wait for, so an on-time pre-market start would only have sent
  orders into a closed market; the cycle now starts at `14:40 UTC`, after the open (see
  [deployment](/deployment#if-github-skips-or-delays-the-run)).
- **A deadline.** A batch that has not finished within `BATCH_DEADLINE_SECONDS`
  is abandoned, ticker by ticker, for live calls. The worst a slow batch can
  do is cost what a cycle costs today. It cannot cost a session.

<Warning>
  Starting pre-market (the `--premarket` flag, which the scheduled workflow no
  longer passes) gives up the broker's own market-closed gate, which would
  otherwise refuse every early run. `config.market_calendar.is_trading_day`
  stands in for it instead: a weekend or a listed NYSE holiday is skipped
  before anything is fetched, at zero cost. What that calendar cannot see — a
  half day, or an unscheduled closure — still reaches the broker's own gate,
  which refuses the orders either way.
</Warning>

The job's own timeout has to cover the worst case of both waits, not just
context gathering: roughly 45 minutes to gather 80 tickers, plus up to
`BATCH_DEADLINE_SECONDS` for the screen batch, plus up to the same again for
whatever it escalates — about 115 minutes worst case, against a 180-minute
ceiling. Position management is run immediately after the open book is read,
before either batch is submitted, specifically so a run that dies during
that wait has already protected and trimmed the book.

## The cache breakpoint has to be on the system prompt

`cache_control` as a top-level request parameter caches *the last cacheable
block*, and in this request that is the per-ticker user prompt — a different
string every call. The cycle did that until 20 Sep, and the journal recorded
what it cost: across 934 calls, **1,869,345 tokens written to cache and zero
ever read**. Opus reported 406 uncached input tokens in total, because the
whole request was billed as a cache write at 1.25× and then discarded. The
premium came to 10.7% of spend for no benefit at all.

The breakpoint now rides the system block, so the volatile half of the request
falls outside it. Two bounds are worth knowing: the cache is scoped per model,
so the screen and the full model each pay one write per cycle, and a prompt
under the model's minimum cacheable prefix does not cache at all.
`cache_read_input_tokens` in the journal is how either shows up — which is why
it is recorded rather than assumed.

## A stage that is not billed at all

`SCREENING_BASE_URL` points the screening stage at any OpenAI-compatible
endpoint — Ollama, llama.cpp, vLLM, LM Studio — so the cheap stage can run on
a model nobody bills for. Set `SCREENING_MODEL` alongside it; unset, the screen
is Claude Haiku exactly as before.

Only the screen. The call that decides what trades stays Claude, and a test
reads `call_llm`'s source to keep it that way.

<Warning>
  This cannot be a model on the GitHub-hosted runner: `ubuntu-latest` is four
  CPUs with no GPU and a disk discarded between runs, so weights would be
  re-downloaded every cycle and eighty CPU inferences would not fit in a job
  that already spends 42 of its 90 minutes on I/O. It has to point at a
  self-hosted runner or a machine on the network.
</Warning>

An endpoint that is unreachable, errors, or answers in prose raises the same
`LLMError` a failed Claude screen does, and the funnel already handles that by
asking the full model. The worst a flaky local model can do is cost a cycle its
saving; it cannot reach a trade.

### Very cheap often beats free, for this workload

<Warning>
  **Every candidate measured so far fails the escalation-recall floor, and the
  screen is still Claude Haiku.** The numbers are in [what the candidates
  actually scored](#what-the-candidates-actually-scored) below. Read the rest
  of this section as how to wire and grade a candidate, not as a
  recommendation to flip one on: the prices are real and the recall is not
  there. Nothing here is a setting to copy into production today.
</Warning>

Two independent reviews of this seam (one run in the session that built it,
one run separately with no visibility into the first) landed on the same
answer without comparing notes first: for ~80 calls/day of ~3,600-token
prompts, a very cheap **paid** model is the better starting point over most
free tiers, not a worse one. The volume is small in total but bursty --
eighty multi-thousand-token calls fired close together in one job -- and that
is exactly the shape free tiers cap hardest: Groq's free tier for its
strict-JSON-capable models is 200,000 tokens/day and 8,000 tokens/minute,
which this workload alone can exceed on the tokens-per-minute side. Google's
free Gemini tier fits the volume but trains on free-tier prompts by default.
Paying instead runs about **$0.60-$1.00/month** at this size and removes both
problems.

<Warning>
  `OpenAICompatibleProvider` always sends `response_format` in OpenAI's
  *strict* `json_schema` mode, with no fallback to loose JSON. A provider that
  does not honour strict mode either 400s (the ticker falls through to the
  full model -- safe, but the screen never ran) or returns best-effort JSON
  that can miss the schema (`LLMError` -> same fallback). Confirm strict
  support before trusting a candidate's number, not after.
</Warning>

### What the screen actually costs

Measured from 465 recorded screening calls: 2,439 input tokens, 1,189 of them
the cacheable prompt head, and 510 output tokens per call. At 68 screened
tickers a cycle and 21 trading days:

| Screening model | $/month | vs Haiku |
| --- | --- | --- |
| `claude-haiku-4-5`, cache working | $7.29 | — |
| `openai/gpt-oss-20b` on DeepInfra | $0.26 | 28x cheaper |
| `openai/gpt-oss-20b` on Groq | $0.61 | 12x cheaper |
| `Qwen3.6-35B-A3B` on DeepInfra | $1.47 | 5x cheaper |
| `gemini-3.5-flash-lite` | $3.37 | 2.2x cheaper |

The Haiku row is the one to read first. It is *already* lower than the $9.25
this stage used to cost, because the cache breakpoint fix landed — which
means the cheap-screen argument is now being made against a smaller number
than it was originally made against. What is left to save is single-digit
dollars a month, and the recall floor below is what it has to be worth.

### Strict JSON is a property of the host, not the model

This is the constraint that eliminates most candidates, and it is easy to get
wrong because it looks like a question about the model.
`OpenAICompatibleProvider` sends strict `json_schema` with no fallback, so the
*serving endpoint* is what has to do constrained decoding:

- **DeepSeek's own API cannot.** It supports `json_object` but rejects
  `response_format.type = "json_schema"` outright. Every screening call would
  400 and every ticker would fall through to the full model -- more expensive
  than changing nothing at all.
- **Alibaba DashScope is partial**: only the newer Qwen3.7/3.8 series enforce
  a schema rather than merely suggesting one.
- **DeepInfra, Groq, Fireworks and Together do it server-side**, for whatever
  weights they host.

So choose the host first. The model is then a menu, including the Chinese
open-weight ones -- served from US infrastructure, which also avoids sending
every prompt to an endpoint whose terms permit training on it.

**The cheapest reachable option: `openai/gpt-oss-20b` on DeepInfra**, at
$0.03/$0.14 per Mtok.

```bash
SCREENING_BASE_URL=https://api.deepinfra.com/v1/openai
SCREENING_MODEL=openai/gpt-oss-20b
SCREENING_API_KEY=<your DeepInfra key>
```

Key from [deepinfra.com](https://deepinfra.com) -> Dashboard -> API Keys.

<Warning>
  Groq serves the same model and documents constrained decoding on exactly
  this family, but as of 20 Sep 2026 its console answers "Developer tier
  upgrades are temporarily unavailable due to high demand", so the paid tier
  cannot be joined. The free tier's request caps and data-use policy both rule
  it out for an 80-ticker daily cycle. The `openai/gpt-oss-20b` row in
  `orchestrator/pricing.py` is therefore DeepInfra's: an open-weight model's
  price belongs to whoever serves it, the journal records only the name, and
  serving it from Groq instead makes that row wrong by about 2.4x with nothing
  to detect it.
</Warning>

<Note>
  Wanting a frontier Chinese model here is understandable and probably
  misspent. The screen is a NEUTRAL-or-not call over a short context: it needs
  schema compliance and calibration, not intelligence. GLM-4.6 costs 13x what
  `gpt-oss-20b` does to answer a question neither struggles with. If you want
  one regardless, `Qwen3.6-35B-A3B` on DeepInfra is the sensible pick -- still
  5x under Haiku -- and `compare_screening.py` is what settles whether the
  extra capability actually buys any recall.
</Note>

**The alternative: Google Gemini `gemini-3.5-flash-lite`.** $0.30/$2.50 per
Mtok, a 1M-token context, honours strict `json_schema` on the normal
(non-batch) request path, and does not reason by default -- which matters
because of the caveat below.

```bash
SCREENING_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
SCREENING_MODEL=gemini-3.5-flash-lite
SCREENING_API_KEY=<your AI Studio key>
```

Get the key from [aistudio.google.com](https://aistudio.google.com) -> "Get
API key", created in a project **with billing enabled** -- that's what moves
prompts off the free tier's training-data policy and off its request caps.
This is an account and billing action only you can take; nothing here can do
it for you.

<Warning>
  Model names expire. `gemini-2.5-flash-lite` was this page's recommendation
  until 20 Sep 2026, when the endpoint began answering
  `404 ... no longer available to new users`. That is a clean failure -- the
  screen falls through to the full model, so it costs money rather than
  making a bad trade -- but it is silent unless something asks. The
  **screening check** workflow is what asks; run it after any change to
  `SCREENING_MODEL`. The prices above were verified the same day and carry
  the same expiry risk.
</Warning>

<Note>
  Both rows are in `orchestrator/pricing.py`, so the screening stage appears
  in the measured bill instead of pricing as `None` and quietly leaving it. A
  self-hosted endpoint has no row and still costs `None`, which is the honest
  answer for someone else's GPU.
</Note>

<Note>
  `gpt-oss-20b` reasons by default and has no true "off" -- only low, medium
  or high effort. `orchestrator/llm.py`'s `NO_REASONING_INSTRUCTION` and best-
  effort `reasoning_effort: "low"` (sent automatically whenever
  `reasoning=False`, which the screen always asks with) cover this, but it is
  worth knowing this model has to be *asked* to reason less, where Gemini
  simply does not reason much to begin with.
</Note>

### Where the three values go

Locally, `.env` — that is what `replay/compare_screening.py` and a local
heartbeat read. For the scheduled cycle they have to be named in
`.github/workflows/heartbeat.yml`'s env block as well, because a secret the
workflow never passes to the step is a secret the cycle cannot read. They are
wired there already, split by what is actually sensitive:

| Value | Where it lives on GitHub |
| --- | --- |
| `SCREENING_BASE_URL` | repository **variable** (Settings -> Secrets and variables -> Actions -> Variables) |
| `SCREENING_MODEL` | repository **variable** |
| `SCREENING_API_KEY` | repository **secret** |

All three unset is the supported default: the screen stays on Claude Haiku.
`tests/test_workflow_keys.py` pins the list, so a fourth setting added to
`config/settings.py` and forgotten in the workflow fails the suite rather
than silently reading blank in production.

The key may also be stored under `GEMINI_API_KEY`, `GOOGLE_API_KEY` or
`GROQ_API_KEY` — the workflow collapses those onto `SCREENING_API_KEY`, which
is the only name the code itself reads. The alternatives exist because the
obvious thing to call a Gemini key is `GEMINI_API_KEY`, and a key stored under
a name nothing reads is silent: the screen just stays on Haiku.

<Note>
  Being silent is the whole problem with this configuration. A key under an
  unread name, a key with no `SCREENING_BASE_URL` behind it, and an endpoint
  that refuses strict `json_schema` all look exactly like "screening is off",
  which is a legitimate state that raises nothing. Run the **screening check**
  workflow (Actions -> screening check -> Run workflow) to make it say so out
  loud: it reports which name carried the key, whether the base URL and model
  are set, and makes one real call through the same provider the cycle uses.
  It never prints a key, and it fails the run when the configuration is
  incoherent. Locally the same check is
  `python backtest/probe_screening.py`.
</Note>

Answering is not agreeing, and the probe only proves the first. A green
screening check still has to be followed by the recall run below before the
endpoint is worth trusting.

### Validating a candidate before flipping it on

```bash
# Nothing calls the candidate; just say how many recorded lines are comparable
python replay/compare_screening.py --limit 200 --dry-run

# A local Ollama model
python replay/compare_screening.py --base-url http://localhost:11434/v1 \
    --model qwen2.5:14b --limit 200

# A hosted free/cheap tier
python replay/compare_screening.py --base-url https://api.groq.com/openai/v1 \
    --model llama-3.1-8b-instant --api-key "$GROQ_API_KEY" --limit 200
```

`compare_models.py` asks which Claude tier is cheapest; this asks a narrower
question -- does *this specific endpoint*, asked exactly as the screen is
really asked (the same trimmed per-ticker system prompt, `reasoning=False`),
agree with what Haiku actually said on the same recorded lines.

<Warning>
  The baseline is the recorded **screen**, never the recorded final signal. On
  a line the screen escalated, those differ -- the screen's own
  NEUTRAL-or-not call versus the full model's directional one -- and grading a
  candidate against the full model would be grading it on a question
  production never asked it. A line with no recorded screen (screening was
  off, or the screen itself errored) is skipped, not counted as a pass.
</Warning>

Two numbers are reported, and they are not interchangeable. **Trade
agreement** (90% floor, same as the staircase walk) is symmetric: it counts a
candidate that flips a NEUTRAL into a trade the same as one that flips a
trade into NEUTRAL. **Escalation recall** (95% floor) is not, and is what
actually gates the verdict: of the lines Haiku's screen called directional,
the share the candidate also escalated. The reason is cost, not pedantry -- a
candidate that quietly turns a tradeable name NEUTRAL costs a trade
production's funnel can never recover, because the full model is never asked
about a NEUTRAL screen. A candidate that escalates a name Haiku would have
screened out costs one avoidable full-model call. A high trade-agreement
score can still hide a candidate that is failing exactly the first way, which
is what recall exists to catch.

<Note>
  The default sample is 200 lines, not 50: at 45/50 (90%) the 95% confidence
  interval is roughly 78-96%, which cannot actually certify a 90% floor. A
  run under 100 comparable lines is flagged in the output as a first look, not
  evidence.
</Note>

Same limits as the staircase walk otherwise: agreement is not correctness,
and a high failure rate silently reverts every one of those lines to the full
model, which erases the saving without ever risking a bad trade.

### What the candidates actually scored

Three endpoints have been graded against the recorded Haiku screen on the same
journal. None passed.

| Candidate | Asked as | Lines | Escalation recall | Failure rate | $/month |
| --- | --- | --- | --- | --- | --- |
| `claude-haiku-4-5` | production's own screen | — | 100% by construction | — | $7.29 |
| `gemini-3.5-flash-lite` | reasoning off | 195 | **41%** (32 of 79) | 0% | $2.34 |
| `openai/gpt-oss-20b` (DeepInfra) | reasoning off | 156 | **11%** (7 of 64) | 20% | $0.22 |
| `openai/gpt-oss-20b` (DeepInfra) | `effort=high` | 156 | **5%** (3 of 62) | 20% | $1.46 |

The `$/month` column is what each run measured from its own token usage at 80
tickers, so it will not match the projected table above to the cent — that one
prices every model on Haiku's measured token profile at 68 tickers. A model
that answers more tersely than Haiku comes out cheaper than its projection.

Read the recall column, not the price column. At 41%, Gemini would silently
turn three of every five names Haiku wanted looked at into NEUTRAL — and the
full model is never asked about a NEUTRAL screen, so those trades are not
recoverable further down the funnel. The $4.95/month it saves buys that.

Two things in this table are worth more than the verdict:

- **Gemini's failure rate is 0%.** Every one of its 195 calls answered in the
  schema, so 41% is the model disagreeing, not the endpoint breaking. The
  `gpt-oss-20b` rows are 20%, which means a fifth of those lines never
  produced an answer at all and its recall is measured only on the survivors.
  A cleaner run of that model would very likely score differently; it would
  have to score about nine times better to matter.
- **More thinking made `gpt-oss-20b` worse**, 11% to 5%. That is the opposite
  of the intuition that bought the experiment, and it is why `--effort` exists
  in the check: reasoning is a variable to measure here, not a lever that only
  goes one way. The plausible mechanism is that a reasoning model talks itself
  out of a marginal name, and every name this screen exists to catch is
  marginal.

What none of these numbers say is that Haiku was *right* on the lines it
escalated. Recall measures interchangeability with the incumbent, and on
exactly the lines where two models differ it is silent about which one was
correct. It is the right gate anyway, because the cost of the two errors is
not symmetric — see the floor's reasoning above — but a candidate that scored
95% would still only have earned the right to be tried, not a claim to be
better.

## Stage zero: what the book already holds

A ticker already in the book is asked nothing, by either model. It is
journalled with its context, counted in the cycle report as `held`, and
dropped before the screen.

The reasoning is that the open book is already managed, and not by an opinion.
`PositionManager` walks it every cycle — profit-ladder tranches, stop raising,
ATR trailing stops, re-protecting a naked stop — all arithmetic, all free. A
fresh signal on a held name could only add a top-up, and it was being bought
at the price of the full funnel.

What this gives up is stated where it is configured: the top-up, and the flip
block that rejected a signal opposite to the side held. Neither is
load-bearing — a position that goes wrong is closed by its stop, and one that
goes right is trimmed up the ladder.

With 12 names held against a watchlist of 80, this is about 15% of a cycle's
calls. The direction is the point: model spend goes to the names that could
still become positions, against `MAX_OPEN_POSITIONS` of 40, rather than to the
half of the book that already is one.

<Note>
  It degrades to the old behaviour on its own. If the open book cannot be read
  — a broker error, or webhook mode, where the orchestrator holds no broker
  credentials by design — every ticker is reviewed and the run log says why.
  Skipping a ticker nobody holds is a missed trade; reviewing one that is held
  is a wasted call, and the second is the cheaper mistake.
</Note>

## The funnel

Every ticker is read first by `claude-haiku-4-5` with reasoning off, on the
identical prompt. A NEUTRAL there ends the ticker; anything else goes on to the
full model. Measured on the 16 Sep cycle, per ticker:

| Stage | Model | Reasoning | Measured |
|---|---|---|---|
| Screen | `claude-haiku-4-5` | off | $0.0068 |
| Decide | `claude-opus-5` | `low` | $0.046 |

So a screened ticker costs about a seventh of a decided one, and the cycle's
bill is `80 × $0.0068 + (escalated) × $0.046`. The 16 Sep cycle escalated 41%
of 78 tickers and came to **$2.01**; on a quieter day, less. The saving is bounded by how much of the watchlist has nothing
happening — which, across sixteen single names, fourteen broad funds,
forty-one sector and country funds and nine commodity funds, is usually most
of it.

<Note>
  The watchlist grew from 35 names to 80 in one change, and the funnel is why
  that was affordable. Screening the whole list costs about $0.16; the bill
  only moves for the names something is actually happening to. Widening a list
  that had no screen in front of it would have been a 2.3× bill.
</Note>

<Warning>
  The screen cannot make the system trade more, only less. What it *can* do is
  drop a ticker the full model would have taken a side on, and the live
  journal cannot see that case by construction — the full model was not asked.
  Measure the false-negative rate from a run with `SCREENING_ENABLED = False`
  before trusting the saving; see
  [the journal](/orchestrator/journal#one-json-object-per-ticker-per-cycle)
  for what is and is not recorded.
</Warning>

<Note>
  The system prompt is byte-identical across every ticker in a cycle, so it is
  marked cacheable. Whether it *is* cached depends on the model's minimum
  cacheable prefix, which this prompt may sit under — so the journal records
  `cache_read_input_tokens` rather than assuming a saving. Zero reads across a
  cycle means the line is doing nothing.
</Note>

## Comparing configurations

```bash
python replay/compare_models.py --dry-run                       # plan + call budget
python replay/compare_models.py --only claude-opus-5:medium     # price the incumbent
python replay/compare_models.py --limit 20                      # the walk
```

Every cell replays the **same recorded contexts**, so the only thing that varies
is the configuration. The `$/month` column projects at `CYCLES_PER_TRADING_DAY`
(now 1, derived from the daily heartbeat interval) over 21 trading days.

```
configuration                $/call   $/month   agree  trade-agree  out tok
opus-5 / low                $0.0221     $13.9    100%         100%      600
opus-5 / medium             $0.0446     $28.0    100%         100%     1500
sonnet-5 / low              $0.0118      $7.4     95%          95%      900  <- cheapest acceptable
sonnet-5 / medium           $0.0228     $14.3    100%         100%     2000
haiku-4-5 / low             $0.0069      $4.3     70%          70%     1100  (below floor)
```

<Note>
  Note `opus-5 / low` at $13.9 undercutting `sonnet-5 / medium` at $14.3. **A
  stronger model thinking less can be cheaper than a weaker model thinking
  more** — it spends fewer tokens reaching the same answer. Fixing the model and
  then tuning effort never finds that cell.
</Note>

## Walk a staircase, not a grid

Model tier and effort are one surface, and a full grid pays for every expensive
corner to find the cheap one. Instead:

<Steps>
  <Step title="Enter top-left">
    Strongest tier, cheapest effort. Budget-bounded, and unambiguous to step
    away from — a pass prunes one direction, a fail prunes the other.
  </Step>
  <Step title="Pass → step down a tier">
    Record the cost as the incumbent. Every cell to the right of a pass costs
    more, so it cannot win regardless of quality.
  </Step>
  <Step title="Fail → step right one notch">
    Presume lower tiers fail at that effort too. Cap the rightward walk at a
    notch or two: quality in effort is only weakly monotone.
  </Step>
  <Step title="Stop when nothing unprobed projects cheaper">
    The incumbent is the answer.
  </Step>
</Steps>

## What the comparison cannot tell you

<Warning>
  **Agreement is not correctness.** A cell that matches the incumbent 100% of
  the time is interchangeable *with the incumbent* — which only helps if the
  incumbent was right, and nothing here knows that.

  There is no ground truth for a trading signal until the market moves. Only
  [Scoring](/scoring), against realised returns, can say whether any
  configuration produces signals worth trading.
</Warning>

Two more limits worth stating:

- **The floor is pre-registered** (default 90% trade-agreement) before any cell
  runs. A floor read off the results afterwards is a story fitted to them.
- **Every cell starts with a cold cache** — the cache is per model, and effort
  is part of its key — so the costs reported are an upper bound on steady state.

`trade-agree` is the column that matters: the share of contexts where both
configurations agreed on whether to trade *at all*. A signal that matches on
direction but lands the other side of `MIN_CONVICTION` produces a different
portfolio.
