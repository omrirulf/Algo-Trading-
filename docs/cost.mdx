Cost used to be an estimate in this project: an assumed output length times a
list price. That estimate drove a real decision — how many tickers to watch —
which is the wrong way round. `response.usage` is now recorded on every call,
so the number in the journal is measured.

```json
"usage": {
  "model": "claude-opus-5",
  "input_tokens": 1420,
  "output_tokens": 1512,
  "cache_read_input_tokens": 0,
  "cost_usd": 0.0449
}
```

## Where the money goes

At this prompt shape — **~3,600 input tokens** against a thinking response —
**output is most of the bill**, because thinking tokens bill at the output
rate and output is several times input.

<Note>
  This page said ~1,400 tokens until 16 Sep. That was true before the nine
  enrichment sections were added; the prompt is now about 2.5× that, and every
  figure below was measured on the 16 Sep cycle rather than estimated.
</Note>

That ordering matters: **effort is a bigger lever than model tier.**

| | Lever | Effect |
|---|---|---|
| 1 | `USE_BATCH_API` | Halves every call that is not in a hurry — which here is all of them |
| 2 | `EFFORT` | Directly moves the 84% |
| 3 | Model tier | Multiplies both halves |
| 4 | The funnel (`SCREENING_ENABLED`) | Removes whole calls: the share of the watchlist the screen calls NEUTRAL |
| 5 | `SKIP_HELD_TICKERS` | Removes whole calls: the share of the watchlist already in the book |
| 6 | Watchlist length | Linear in calls |
| 7 | `HEARTBEAT_INTERVAL_MINUTES` | Linear in calls |
| 8 | Prompt caching | Only touches the 16% — and only when the breakpoint is placed correctly, see below |

## Half price, for waiting

The Message Batches API costs half of what the same request costs live. The
cycle is the ideal shape for it: eighty independent prompts, none of which
needs an answer in the same second.

What it costs is immediacy — a batch may take up to 24 hours, though a small
one usually finishes in minutes. Two things buy that back:

- **The cycle starts pre-market.** The `12:35 UTC` cron gathers context, then
  waits on the batch in hours the strategy was not trading in anyway.
- **A deadline.** A batch that has not finished within `BATCH_DEADLINE_SECONDS`
  is abandoned, ticker by ticker, for live calls. The worst a slow batch can
  do is cost what a cycle costs today. It cannot cost a session.

<Warning>
  Starting pre-market gives up the cheap market-closed gate, which would
  otherwise refuse every early run. A holiday gathers context and pays for a
  batch whose signals the engine then refuses — roughly ten cycles a year,
  against a halved bill on the other 250. Only the run that is *meant* to
  start early passes `--premarket`; every other caller still exits at once
  when the market is shut.
</Warning>

## The cache breakpoint has to be on the system prompt

`cache_control` as a top-level request parameter caches *the last cacheable
block*, and in this request that is the per-ticker user prompt — a different
string every call. The cycle did that until 20 Sep, and the journal recorded
what it cost: across 934 calls, **1,869,345 tokens written to cache and zero
ever read**. Opus reported 406 uncached input tokens in total, because the
whole request was billed as a cache write at 1.25× and then discarded. The
premium came to 10.7% of spend for no benefit at all.

The breakpoint now rides the system block, so the volatile half of the request
falls outside it. Two bounds are worth knowing: the cache is scoped per model,
so the screen and the full model each pay one write per cycle, and a prompt
under the model's minimum cacheable prefix does not cache at all.
`cache_read_input_tokens` in the journal is how either shows up — which is why
it is recorded rather than assumed.

## A stage that is not billed at all

`SCREENING_BASE_URL` points the screening stage at any OpenAI-compatible
endpoint — Ollama, llama.cpp, vLLM, LM Studio — so the cheap stage can run on
a model nobody bills for. Set `SCREENING_MODEL` alongside it; unset, the screen
is Claude Haiku exactly as before.

Only the screen. The call that decides what trades stays Claude, and a test
reads `call_llm`'s source to keep it that way.

<Warning>
  This cannot be a model on the GitHub-hosted runner: `ubuntu-latest` is four
  CPUs with no GPU and a disk discarded between runs, so weights would be
  re-downloaded every cycle and eighty CPU inferences would not fit in a job
  that already spends 42 of its 90 minutes on I/O. It has to point at a
  self-hosted runner or a machine on the network.
</Warning>

An endpoint that is unreachable, errors, or answers in prose raises the same
`LLMError` a failed Claude screen does, and the funnel already handles that by
asking the full model. The worst a flaky local model can do is cost a cycle its
saving; it cannot reach a trade.

## Stage zero: what the book already holds

A ticker already in the book is asked nothing, by either model. It is
journalled with its context, counted in the cycle report as `held`, and
dropped before the screen.

The reasoning is that the open book is already managed, and not by an opinion.
`PositionManager` walks it every cycle — profit-ladder tranches, stop raising,
ATR trailing stops, re-protecting a naked stop — all arithmetic, all free. A
fresh signal on a held name could only add a top-up, and it was being bought
at the price of the full funnel.

What this gives up is stated where it is configured: the top-up, and the flip
block that rejected a signal opposite to the side held. Neither is
load-bearing — a position that goes wrong is closed by its stop, and one that
goes right is trimmed up the ladder.

With 12 names held against a watchlist of 80, this is about 15% of a cycle's
calls. The direction is the point: model spend goes to the names that could
still become positions, against `MAX_OPEN_POSITIONS` of 40, rather than to the
half of the book that already is one.

<Note>
  It degrades to the old behaviour on its own. If the open book cannot be read
  — a broker error, or webhook mode, where the orchestrator holds no broker
  credentials by design — every ticker is reviewed and the run log says why.
  Skipping a ticker nobody holds is a missed trade; reviewing one that is held
  is a wasted call, and the second is the cheaper mistake.
</Note>

## The funnel

Every ticker is read first by `claude-haiku-4-5` with reasoning off, on the
identical prompt. A NEUTRAL there ends the ticker; anything else goes on to the
full model. Measured on the 16 Sep cycle, per ticker:

| Stage | Model | Reasoning | Measured |
|---|---|---|---|
| Screen | `claude-haiku-4-5` | off | $0.0068 |
| Decide | `claude-opus-5` | `low` | $0.046 |

So a screened ticker costs about a seventh of a decided one, and the cycle's
bill is `80 × $0.0068 + (escalated) × $0.046`. The 16 Sep cycle escalated 41%
of 78 tickers and came to **$2.01**; on a quieter day, less. The saving is bounded by how much of the watchlist has nothing
happening — which, across sixteen single names, fourteen broad funds,
forty-one sector and country funds and nine commodity funds, is usually most
of it.

<Note>
  The watchlist grew from 35 names to 80 in one change, and the funnel is why
  that was affordable. Screening the whole list costs about $0.16; the bill
  only moves for the names something is actually happening to. Widening a list
  that had no screen in front of it would have been a 2.3× bill.
</Note>

<Warning>
  The screen cannot make the system trade more, only less. What it *can* do is
  drop a ticker the full model would have taken a side on, and the live
  journal cannot see that case by construction — the full model was not asked.
  Measure the false-negative rate from a run with `SCREENING_ENABLED = False`
  before trusting the saving; see
  [the journal](/orchestrator/journal#one-json-object-per-ticker-per-cycle)
  for what is and is not recorded.
</Warning>

<Note>
  The system prompt is byte-identical across every ticker in a cycle, so it is
  marked cacheable. Whether it *is* cached depends on the model's minimum
  cacheable prefix, which this prompt may sit under — so the journal records
  `cache_read_input_tokens` rather than assuming a saving. Zero reads across a
  cycle means the line is doing nothing.
</Note>

## Comparing configurations

```bash
python replay/compare_models.py --dry-run                       # plan + call budget
python replay/compare_models.py --only claude-opus-5:medium     # price the incumbent
python replay/compare_models.py --limit 20                      # the walk
```

Every cell replays the **same recorded contexts**, so the only thing that varies
is the configuration. The `$/month` column projects at `CYCLES_PER_TRADING_DAY`
(now 1, derived from the daily heartbeat interval) over 21 trading days.

```
configuration                $/call   $/month   agree  trade-agree  out tok
opus-5 / low                $0.0221     $13.9    100%         100%      600
opus-5 / medium             $0.0446     $28.0    100%         100%     1500
sonnet-5 / low              $0.0118      $7.4     95%          95%      900  <- cheapest acceptable
sonnet-5 / medium           $0.0228     $14.3    100%         100%     2000
haiku-4-5 / low             $0.0069      $4.3     70%          70%     1100  (below floor)
```

<Note>
  Note `opus-5 / low` at $13.9 undercutting `sonnet-5 / medium` at $14.3. **A
  stronger model thinking less can be cheaper than a weaker model thinking
  more** — it spends fewer tokens reaching the same answer. Fixing the model and
  then tuning effort never finds that cell.
</Note>

## Walk a staircase, not a grid

Model tier and effort are one surface, and a full grid pays for every expensive
corner to find the cheap one. Instead:

<Steps>
  <Step title="Enter top-left">
    Strongest tier, cheapest effort. Budget-bounded, and unambiguous to step
    away from — a pass prunes one direction, a fail prunes the other.
  </Step>
  <Step title="Pass → step down a tier">
    Record the cost as the incumbent. Every cell to the right of a pass costs
    more, so it cannot win regardless of quality.
  </Step>
  <Step title="Fail → step right one notch">
    Presume lower tiers fail at that effort too. Cap the rightward walk at a
    notch or two: quality in effort is only weakly monotone.
  </Step>
  <Step title="Stop when nothing unprobed projects cheaper">
    The incumbent is the answer.
  </Step>
</Steps>

## What the comparison cannot tell you

<Warning>
  **Agreement is not correctness.** A cell that matches the incumbent 100% of
  the time is interchangeable *with the incumbent* — which only helps if the
  incumbent was right, and nothing here knows that.

  There is no ground truth for a trading signal until the market moves. Only
  [Scoring](/scoring), against realised returns, can say whether any
  configuration produces signals worth trading.
</Warning>

Two more limits worth stating:

- **The floor is pre-registered** (default 90% trade-agreement) before any cell
  runs. A floor read off the results afterwards is a story fitted to them.
- **Every cell starts with a cold cache** — the cache is per model, and effort
  is part of its key — so the costs reported are an upper bound on steady state.

`trade-agree` is the column that matters: the share of contexts where both
configurations agreed on whether to trade *at all*. A signal that matches on
direction but lands the other side of `MIN_CONVICTION` produces a different
portfolio.
