---
title: "The Article Probe"
description: "One recorded context, with the articles behind its search results fetched and handed to the model: what full text would add, before anything is built"
---

The news block is a headline and Google's ~150-character snippet per result.
The probe asks, on **one** example, what changes when the model also gets the
start of each article: how many words that adds, how much of it is the story
rather than the page around it, and what the model then says and spends.

```bash
python replay/article_probe.py --dry-run                     # which line, which pages; no network
python replay/article_probe.py --no-model                    # fetch and measure only
python replay/article_probe.py --ticker NVO --day 2026-09-28
python replay/article_probe.py --build-scraper               # Scraper Studio's AI builds the site's scraper
python replay/article_probe.py --collector c_...              # build on (or use) a collector that exists
python replay/article_probe.py --scraper-trigger 'https://api.brightdata.com/dca/trigger?collector=c_...'
```

It runs by hand (**Actions → article probe**) and, like the
`baseline-compare` workflow, on its own pull request when it changes, because
a manual workflow does not exist until it reaches `main`. It never trades and
holds no broker key.

## Where the text comes from

| Source | How | Covers |
| --- | --- | --- |
| Web Unlocker | the zone the news fetch already uses, then one generic extractor (trafilatura) cuts the story out of the page | every site, one code path |
| Scraper Studio | a scraper its AI builds through the API (`--build-scraper`, or `--collector` to build on one that exists), or an existing one by its trigger URL | the one site it was built for |

Both are cut to the same number of words (`--words`, default 300) before the
model sees them, so a difference between the two is a difference in *which*
words, not in how many. Quote pages, symbol pages, filings and videos are
skipped without a request; Google's `/goto` redirect stubs are followed once.

## The Scraper Studio side

Nobody has to open the dashboard. Dispatch the workflow with `build_scraper`
on, and the probe has Scraper Studio's AI build a scraper for the site from one
of the line's own article links, with the same three API calls Bright Data's
CLI makes for `bdata scraper create`:

1. `POST /dca/collector` creates an empty collector;
2. `POST /dca/collectors/{id}/automate_template` asks the AI to build it from
   one example page and a description of the fields wanted (`url`, `title`,
   `published_at`, `author`, and `body`, the article's own text), waiting out
   the AI's parallel-build cap (HTTP 429) the way the CLI does;
3. `GET /dca/collectors/{id}/automate_template/progress` until it is done,
   within 15 minutes.

The example page is one the Unlocker could read, when one could: a page that
loads is one the AI can learn from. A server error is retried like the CLI
retries it, until it says the same thing twice: then it is an answer, not a
hiccup. Every refusal is reported with Bright Data's own error headers.

`scraper_collector` (`--collector c_…`) builds on a collector that already
exists instead of creating another. One that a failed build left behind is
finished rather than joined by a second stub; one that is already built is
used as it is.

It then runs the new scraper on the same pages, and the report prints its
trigger URL, `https://api.brightdata.com/dca/trigger?collector=c_…`, so a
later run can reuse it through the `scraper_trigger` input or the repository
variable `BRIGHTDATA_SCRAPER_TRIGGER` instead of building another. A trigger
URL, when given, always wins over a build.

<Warning>
  A build leaves the collector in the account's Scraper Studio, even when the
  build fails. Bright Data documents no API to delete one, so it is only built
  when asked for by name, never on a pull-request run; delete it in the
  dashboard when done, or build on it with `scraper_collector`.
</Warning>

Bright Data's library of ready-made scrapers is looked up too, and any named
for the site are listed. A name match is a lead, not an answer: the one
Bright Data's CLI knows for Yahoo returns company data, not articles.

The probe sends the Bright Data token only to `https://api.brightdata.com/`,
and refuses any other trigger URL. Both of Bright Data's job APIs are
understood: a `snapshot_id` is collected from the datasets API, a
`collection_id` or `response_id` from the collector API, and a list is taken
as the records themselves. The realtime trigger (`/dca/trigger_immediate`)
gets one page per request, as the CLI sends it. When a batch job brings back
no article text, its job log (`GET /dca/log/{id}`) is read, so the report
says whether the pages failed or were read and yielded nothing.

## What the model is asked

The production call, unchanged (`heartbeat.call_llm`: same system prompt,
model, effort and schema), on the same context rendered several ways, each
asked `--repeats` times (default 2):

| Prompt | The NEWS block |
| --- | --- |
| `headlines` | exactly as recorded |
| `unlocker` | every result that yielded an article gets its opening words under its headline |
| `unlocker-named` | the same, but only for the stories that name the company (asked when some do not) |
| `unlocker+scraper` | the Unlocker's text, plus the scraper's for the pages the Unlocker could not read (asked when the scraper filled one) |
| `unlocker-site` | only the site's results, text from the Unlocker |
| `scraper-site` | the same results, text from the scraper |

The last two include only results *both* sources read, so they differ in
nothing but where the words came from.

## What it reports

- **What the Unlocker got**, per result: page size, article length, words
  sent, the share of those words that look like page furniture (sign-up
  boxes, "story continues", disclosures), whether the story names the company
  at all, and why a result has no text (skipped, refused, paywall or teaser?).
- **Scraper Studio**, per site result: the same measures, plus how much of
  each source's text the other also has. Near 100% both ways means both read
  the same story.
- **What the model read and said**, per prompt: prompt words, input and
  output tokens, cost per call, and every answer; then each prompt's first
  rationale.

The run's artifact keeps everything: each article's text, each prompt as sent,
the scraper's records and every answer.

## What it costs

About a dozen Unlocker requests, the scraper's records if one is given, and
four to twelve model calls at the production price (a fifth of a cent each).

## What it cannot decide

One context and a handful of calls show what the model reads and what it
costs. They cannot show that it trades better: that takes many contexts
scored against prices, which is what saving the text at signal time and
testing it at a checkpoint would be for. The pages are also fetched when the
probe runs, not when the line was written, so a story edited since then is
read as it is now.
