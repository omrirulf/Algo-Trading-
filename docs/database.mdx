Two append-only JSON-lines files hold everything this system has ever seen:

| File | Written by | Answers |
|---|---|---|
| `logs/journal/` (one file per month, read joined) | `orchestrator/journal.py` | What was in front of the model when it said that? |
| `logs/execution_audit.log` | `app/logger.py` | What did the engine *do* with the signal? |

They are excellent at being a record and poor at being asked questions. `grep`
finds a line; it does not tell you whether conviction has drifted upward over
six weeks, which rejection reason bites most often, or what the archive cost to
produce. `store/build_db.py` loads both files into SQLite so those become one
query each.

```bash
python store/build_db.py          # load both logs
python store/query.py daily       # signals, conviction and cost per day
```

## The database is derived, not authoritative

This is the decision everything else follows from. The log files remain the
system of record: they are what the orchestrator writes, what git carries
between runs, and what will still be readable with `grep` in ten years. The
database is an index over them, and `--rebuild` throws it away and reloads from
scratch in seconds.

<Note>
  That single property is what makes this safe to add to a system that trades.
  A corrupt index costs a rebuild. It never costs a cycle, and it never costs a
  record.
</Note>

Two consequences, both deliberate.

**Every row keeps its source line verbatim.** The extracted columns cover the
queries worth indexing; everything else is reachable through SQLite's built-in
JSON functions. A field nobody anticipated is a query away rather than a
migration away:

```sql
SELECT ticker,
       ROUND(AVG(json_extract(raw, '$.context.technicals.rsi14')), 1) AS mean_rsi,
       ROUND(AVG(conviction), 2) AS mean_conviction
FROM signals GROUP BY ticker ORDER BY mean_rsi DESC;
```

**Loading is idempotent.** Rows are keyed on a content hash of the source line,
so re-loading a journal that has grown by one line inserts one row. The natural
way to run this is after every cycle, over a file that is append-only and
almost entirely unchanged.

```
$ python store/build_db.py
signals: 35 new, 1120 already loaded, 0 unreadable (1155 lines)
executions: 2 new, 61 already loaded, 0 unreadable (63 lines)
```

## One parser, two sources

Journal rows are built by `analysis.reader.entry_from` — the same function the
file-based scorer uses. Two parsers over one format drift, and the drift would
surface as a report that disagrees with the file it came from.

So the scorer gives the same answer either way, and can now skip months it does
not need:

```bash
python analysis/score_journal.py                        # from the file
python analysis/score_journal.py --db                   # from the index
python analysis/score_journal.py --db --since 2026-10-01
```

## Tables

`signals` and `executions` mirror the two log files. The `decisions` view joins
them on the order id the journal already records:

```sql
CREATE VIEW decisions AS
SELECT s.ts_utc, s.ticker, s.bias, s.conviction, ..., e.quantity, e.entry_price, e.stop_price
FROM signals s
LEFT JOIN executions e ON e.order_id = s.order_id AND s.order_id IS NOT NULL;
```

That join is the one [Next Steps](/next-steps) listed as missing. Close-to-close
returns ignore the stop-loss, so a call that was right about direction and
stopped out on the way there scores as a win. `decisions` carries the size,
entry and stop the engine actually chose, which is what it takes to ask about
filled trades rather than about paper moves.

It is a `LEFT JOIN` on purpose: most signals never become orders, and a
rejection is data.

Since 26 Sep 2026 `executions` also holds the audit log's `position_managed`
lines — the profit ladder and the stops — which the loader used to drop as
unreadable, because their ticker is under `action.ticker` rather than
`result.ticker`. `status` is the action (`stop_raised`, `tranche_taken`,
`held`, ...), `quantity` what it closed, `stop_price` the stop it left. That
is the only change to the local index: the `executions` row count grows by
those lines (146 in the first month), and `decisions` is unchanged, because a
ladder order is never the entry order a journal line records (checked on the
real logs by `tests/test_archive_capture.py`). Nothing that scores reads the
index.

## Canned queries

Each is ordinary SQL, printed with `--explain`. They are starting points to
copy and change, not an API.

| Query | Answers |
|---|---|
| `summary` | How much is in here, over what span, and how did the engine rule? |
| `daily` | Volume, bias split, mean conviction and cost per day — the drift check |
| `tickers` | Which names get called, how confidently, and which actually trade |
| `rejections` | Which guardrail bites most often, and at what conviction |
| `costs` | Tokens and dollars by day and model |
| `health` | Missing-data and error rates per day |
| `trades` | Signals that became real orders, with size and stop |
| `errors` | Cycles that failed, newest first |

## Nothing here can trade, or edit the record

`store/` is the only package in this project that writes anything, which is
exactly why it has a boundary drawn around it. Four CI invariants hold it:

- `store/` contains no order path and imports no broker SDK.
- `store/` may write through `sqlite3` and nowhere else — it cannot append to,
  truncate or delete the logs it reads. An index that can edit its own source
  is a second, unreviewed way to change the record of what was decided.
- `build_db.py --rebuild` may delete the database and its WAL sidecars. An
  `unlink` reaching anything else fails the build.
- Every SQLite connection opened from `analysis/` uses the `mode=ro` URI. A
  plain `connect()` *creates* the file it is pointed at, which would quietly
  make the scorer a writer through a door no grep was watching.

`store/query.py` inherits the last one: an `UPDATE` typed into `--sql` comes
back as `attempt to write a readonly database`.

## The remote archive

SQLite makes the logs queryable. It does not stop them having to live in git.

The heartbeat commits the journal back to the repository after every cycle,
because a discarded runner would otherwise lose it. At 80 tickers and one
cycle a day that is 80 lines a day, and journal lines carrying a full context
run to several kilobytes each — order of tens of megabytes a month,
permanently, because git history does not forget. The figure was written when
the list was 35 names deep and the cycle ran hourly; the list has since more
than doubled while the cadence dropped to daily, which is roughly a wash.

`store/push_remote.py` copies both logs to a Postgres database (Supabase), over
PostgREST:

```bash
python store/push_remote.py --print-schema   # run this in the SQL editor once
python store/push_remote.py                  # send what the remote is missing
python store/push_remote.py --all            # backfill everything
python store/push_remote.py --dry-run        # count, send nothing
```

Set `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` to switch it on. Leave them unset
and the push prints that there is no remote and exits 0 — not having one is a
state, not a failure, so a repository that never configures this does not have
a permanently red heartbeat.

`SUPABASE_SERVICE_KEY` holds a **secret key** (`sb_secret_…`), created for this
job alone under the name `github-archive` in **Settings → API Keys →
Publishable and secret API keys**. It is not the legacy `service_role` key:
Supabase keeps the legacy JWT keys working only until the end of 2026, and this
archive has to run until the experiment ends in June 2027. A secret key is
sent on the `apikey` header only (`store.remote.auth_headers`); Supabase's
migration guide says the same key as `Authorization: Bearer` is parsed as a JWT
and refused. Measured on this project on 26 Sep 2026 with the new-style
publishable key: `apikey` alone answered 200; a different non-JWT Bearer value
answered 401 ("Expected 3 parts in JWT"); a made-up secret key answered 401
("Invalid API key"). A legacy JWT key, if one is ever set, is still sent both
ways, as it needs.

A state that is still said out loud. The project was found paused on 26 Sep
2026 because every push had printed "No remote archive configured" and
nothing read it: a free Supabase project nothing writes to is paused after
about a week, and the [Supabase starter](/deployment#the-supabase-starter)
lives in the same project. So the heartbeat runs the push with
`--status logs/archive_status.json`, which writes down the last attempt, the
last success and a short reason (`not configured`, `project paused or
unreachable`, `HTTP <code>`; never the server's own text), commits it, pages
the phone the same day a push fails, and has the brief warn every day it is
not configured. That file is the one thing `store/` writes outside SQLite,
and the CI guardrail names the exact line.

### It is never in the trading path

The push is a workflow step *after* the journal is written and committed, not a
call inside the cycle.

<Note>
  This is the property that makes a network dependency acceptable at all. A
  failed push cannot cost a signal: the line is already on disk and already in
  git, and the next push catches up on its own.
</Note>

Two CI invariants hold it there. `orchestrator/` may not import `store/` at
all — checked by walking the AST, so the push cannot be called from a cycle by
accident — and the Supabase key has exactly one reader, `store/remote.py`, the
same rule the broker credential lives under.

That is also why the push step in `heartbeat.yml` is allowed to fail loudly
rather than being marked advisory. This repository has been bitten before by a
check made non-blocking "just in case"; here the ordering means there is
nothing to protect.

### Catching up without a bookmark

The runner is discarded after every cycle, so any local record of where the
push left off would be wrong on the next one. Instead the push asks the remote
for its newest `ts_utc` and sends everything at or after it.

Inclusive at the boundary, deliberately: several rows share a timestamp, and an
exclusive comparison would drop the siblings of whichever one happened to be
newest. The overlap costs nothing, because `line_hash` is the remote primary
key and the insert is `on conflict do nothing` — the same content hash that
makes the local load idempotent.

Rows with no timestamp are always sent. There is no honest way to place them
against a watermark, and dropping them would quietly lose exactly the
malformed cycles most worth reading.

### Verbatim, and queryable

`raw` is `text` remotely too, byte-for-byte as written, and stored once.
Storing it as `jsonb` would silently reformat the line — key order,
whitespace, number rendering — and the archive's whole claim is that it kept
what was written. The parsed form is a view that parses `raw` when it is
read, `signals_json` (and `executions_json`):

```sql
select ticker, raw_json -> 'context' -> 'technicals' ->> 'rsi14' as rsi
from signals_json order by ts_utc desc limit 20;
```

Until 26 Sep 2026 it was a stored generated column, `signals.raw_json` — a
second full copy of every line. Measured on the real journal in Postgres 16,
that took a line from 6.7 KB to 12.6 KB (table, TOAST and indexes): about
120 MB a year at 80 lines a day, of a 500 MB plan, for nothing. The migration
`supabase/2026-09-26_archive_capture.sql` drops it, makes the views, and makes
`decisions` again around the change.

## What else it keeps

The owner's rule of 26 Sep 2026: **store what cannot be got back later, and
what a result would need to be checked again**. The git journal stays the
official record; the archive is a backup and a place to search. Nothing in the
race, the funds or the pre-registration reads it (a CI guardrail, below). No
secret, key or token is ever in what it stores.

| Table / object | One row per | Written by |
| --- | --- | --- |
| `signals`, `executions` | journal line, audit line (ladder lines included) | the heartbeat's push |
| `account_snapshots` | `logs/account.jsonl` line: the paper account after a run | the heartbeat's push |
| `account_fills` | fill the snapshots read, keyed on the broker's fill id | the heartbeat's push |
| `model_calls` | HTTP ask to a model — retries, timeouts, refusals, off-schema answers included | the heartbeat's push |
| `model_io_files` | Storage object: its path, size, SHA-256, calls, withheld | the heartbeat's push |
| Storage `model-io/YYYY/MM/YYYY-MM-DD/<run>-<HHMMSS>.jsonl.xz` | heartbeat run: every call's full request and response body | the heartbeat's push |
| `scoring_prices` | distinct daily bar the race or the funds scored with | `scoring-prices.yml` |
| `scoring_runs` | race or funds run: its `prices_sha256` and what it covered | `scoring-prices.yml` |

### Every model call, in full

`orchestrator/model_io.py` records every ask the cycle makes: the request
**body** exactly as sent (every message, `model`, `max_tokens`,
`reasoning_effort`, the response format) and the response body exactly as
received — for gpt-oss that includes `reasoning_content`, for Claude the
thinking blocks. Never a header, never the client or its configuration, never
a key. It is off unless the heartbeat's `main` opens it, it writes a local
file only (`logs/model_io/`, gitignored), and every function swallows its own
errors, like `journal.record`: a capture that breaks costs the record of a
call, never the call.

Each journal line carries, as `model_calls`, the id of every call made for it
and the SHA-256 of both bodies (`prompt_sha256` over the request as canonical
JSON, `answer_sha256` over the response as received). So any copy of the
bodies — the Storage object, the 90-day workflow artifact
`model-io-<run>-<attempt>` — can be checked with nothing but git:

```python
import hashlib, json, lzma
for line in lzma.open("1812...-144012.jsonl.xz", "rt"):
    call = json.loads(line)
    assert hashlib.sha256(call["request"].encode()).hexdigest() == call["prompt_sha256"]
    # ... and against the journal line whose model_calls names call["call_id"]
```

`model_calls` holds everything but the bodies (who, when, provider, model,
attempt, outcome, HTTP status or error class, latency, token counts, batch id,
parameters, the two hashes); the bodies are in the private Storage bucket
`model-io`, one xz object per run, named with the run id and its start time
so a re-run attempt never overwrites a file. The push is idempotent: rows are
keyed on the call id, an object is never overwritten (a re-send is "already
there"), and the same file always compresses to the same bytes. A Storage upload
that fails fails the push like any other, so the phone hears about it the same
day, and `archive-push.yml` with `model_io_run` sends that run's artifact
again.

**Redaction.** Every record is checked twice for anything credential-shaped —
by the capture before it writes, and by the push before it sends
(`config/redaction.py`: the providers' key prefixes, JSON web tokens, a
`Bearer` or `apikey:` header with a value, and the exact key the provider was
built with). A record that matches is **withheld whole**: its bodies are
dropped, its hashes and a `withheld` marker naming the shape are kept, and the
push counts it in `logs/archive_status.json` (`"withheld"`). A header shape
needs its value too, on purpose: "Emergency Use Authorization" is a headline,
and the journal's own month of prompts trips none of the shapes (a test).

<Warning>
  **The model-io bucket and the new key.** Supabase documents that the new
  secret keys work on the `apikey` header alone across its APIs, Storage
  included — the gateway turns the key into the role the service sees. That
  was measured here for PostgREST, not for Storage. The first push after the
  migration is the measurement: its log says `model-io/...: stored`, and
  `logs/archive_status.json` says `"ok": true`. An `HTTP 403` or `401` from
  Storage alone means it did not accept the key that way; the rows still
  arrive, and the artifact keeps the bodies for 90 days.
</Warning>

The artifact is public, like the repository: any signed-in GitHub user can
download it. The owner decided on 26 Sep 2026 to keep it, as the backup for a
failed upload; it holds nothing more private than the journal, and both key
checks stay. Whether to make the repository private is a to-do before any
real money ([Next steps](/next-steps#going-live-dont-yet-but-heres-what-it-takes)).

### The prices a night scored with

The race (`horse-race.yml`) and the funds (`funds.yml`) score against daily
prices fetched from yfinance that night — prices a vendor may revise or drop
later. Both now run with `--with-prices` (`analysis/price_tape.py`), which
changes no number: their output gains one field, `prices_sha256`, the SHA-256
of the exact bars every price source handed out, and prints that table as one
last line. The workflow splits it off into the artifact `scoring-prices`; the
funds run commits the hash in `logs/funds.json` and `logs/race_gate.json`. A
test runs each output twice, with and without the flag, and compares them byte
for byte apart from that field.

Neither workflow holds a secret, so neither can reach the archive.
`scoring-prices.yml` does: it runs after them (only for their scheduled or
hand-started runs on `main`, never a pull request's), downloads the table,
and pushes it with `push_remote.py --only prices`, which refuses a table that
does not hash to its own `prices_sha256`. `scoring_prices` keeps each distinct
bar once, keyed on what it says, so a year of nights is not a year of copies;
`scoring_runs` keeps each run's hash and, per source and ticker, the dates and
bar count it covered. A night is rebuilt from those two and must hash to the
committed `prices_sha256`; the one case the rebuild cannot tell apart — a bar
revised and then revised back — the hash catches, and the artifact holds the
exact table for 90 days.

### Nothing that decides can read it

A CI guardrail, "Nothing that scores or trades can read the archive": no
module in `analysis/`, `shadow/`, `rules/`, `learn/`, `replay/` or
`orchestrator/` may import `store.remote`, `store.push_remote`,
`store.starter_status`, `store.model_calls` or `store.scoring_prices`; no
module the race or the funds import, however deep, may name
`starter_status.json`, `archive_status.json` or the capture directory; and the
race and funds workflows hold no secret at all. The two status files are read
by the daily brief and the health check (`analysis/book.py`,
`analysis/health.py`) to tell the owner how the archive is doing — neither is
behind the race or the funds.

### How big it gets

Measured on 26 Sep 2026 from the real logs, in Postgres 16 and through the
code that pushes (one real gpt-oss day rebuilt as the capture records it):

| Part | Per item | Per year (252 trading days) |
| --- | --- | --- |
| `signals` (80 lines a day) | 6.7 KB a line | ~135 MB |
| `executions` (~55 a day) | 1.7 KB | ~23 MB |
| `model_calls` (~70 asks a day) | 0.8 KB | ~15 MB |
| `scoring_prices` (~86 tickers x 2 kinds) | 0.3 KB | ~14 MB |
| `account_snapshots` + fills (2 a day) | ~9 KB | ~7 MB |
| `scoring_runs` (3 a night) | 4.5 KB | ~3 MB |
| **Database** | | **~200 MB of 500 MB** |
| Storage `model-io` (~70 asks a day) | about 7 KB a call, xz | **~125 MB of 1 GB** |

The objects are **xz** (the owner's choice of 26 Sep 2026: stronger than gzip,
in a format any computer opens: `xz -d` / `unxz` on Linux and macOS, the
Archive Utility on macOS, 7-Zip on Windows, `lzma` in Python). On the
journal's own text xz is about 40% smaller than gzip at its best setting, so
Storage is about 125 MB a year instead of about 205 MB.

Most of the database is the journal itself; the size fix above is what keeps
it from being twice that. Most of the Storage is the reasoning text (about
22 k characters a call at high effort).

### Nobody can read it but you

The tables run with row-level security **enabled and no policies**. That
combination denies every request carrying the publishable key — the key that is
safe to leak precisely because it should be able to do nothing here. The push
uses a secret key (`github-archive`), which acts as the `service_role` Postgres
role, bypasses RLS, and lives only in a GitHub Actions secret. It was checked
live on 26 Sep 2026: the publishable key reads `[]` from `signals`.

The alternative — an insert-only policy for anon — would let anyone who read
the publishable key append rows to the record of what this system decided. A
journal that strangers can write to is not a journal.

<Warning>
  A Postgres view runs with the permissions of whoever **created** it unless
  told otherwise. The first version of this schema created `decisions` without
  `security_invoker`, and an anon-role probe read 0 rows from `signals` and 1
  row from `decisions` — the tables closed, the view over them wide open. The
  shipped schema sets `security_invoker = on`, and a test pins it.
</Warning>

## What is still true

The local files remain the record. The remote is where the record goes to stop
being git's problem; it is not a reason to stop writing the logs, and the
scorer still reads them.
